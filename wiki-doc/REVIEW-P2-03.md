# Проверка P2-03 — 2026-09-19

Проверены [план](IMPLEMENTATION-PLAN.md), [статус](IMPLEMENTATION-STATUS.md),
реализация расширения модели и его интеграция с facts, gate, регрессией и публикацией.
Предыдущий отчёт не подтверждал приёмку P2-03 полностью: положительные примеры
проходили, но скрывали ошибки границ страницы и реконструкции DDL. Замечания ниже
воспроизведены и исправлены в рабочей копии. P2-04/P2-05 не начинались.

## Исправленные замечания

| Дефект | Исправление и доказательство |
|---|---|
| `CREATE TABLE ...; DO ...;` терял DO без `coverage_notes`; аналогично SET и самостоятельный SELECT | Неразобранные верхнеуровневые операторы создают блокирующий пробел с точной строкой. Три отрицательных сценария проходят полный build и не получают допуск |
| DDL невыбранной таблицы попадал в последний выбранный scope. В примере 13 триггер на orders документировался на странице audit_log | Привязка по целевым объектам, изоляция соседних объявлений, явный пробел для несвязанного DDL. В пример добавлено объявление orders; эталоны разделены на две страницы. Общий GRANT учитывается в каждом затронутом scope |
| `ddl.catalog` обращался к отсутствующему `DropStmt.relation` | DROP использует список объектов, в том числе для удаления нескольких таблиц; таблицы действительно исчезают из финального каталога |
| `ADD PRIMARY KEY` терял список ключей и не менял признаки колонок; `column_catalog` заменял результат ALTER исходным CREATE | Общая структура ограничений сохраняет PK/UNIQUE/FK-колонки, PK устанавливает not-null; финальный DDL сохраняется. Gate также сверяет nullable. Проверены ALTER ADD COLUMN/SET NOT NULL и согласованная подмена nullable |
| Поздний ALTER/RENAME/DROP одного файла мог скрыть конфликт с другим файлом без установленного порядка | Каталог сравнивает финальные состояния каждого файла, включая отсутствие объекта после DROP/RENAME, в обоих порядках входов. Повторный CREATE без IF NOT EXISTS отклоняется |
| Маска INSTEAD OF была указана как 4 вместо 64 | Исправлена по фактическому AST закреплённого pglast; добавлен тест триггера INSTEAD OF на view |
| `GRANT SELECT(id)` терял ограничение прав колонкой, структура facts оставалась нетипизированным object | Сохраняется `privilege_columns`; подмена колонки отклоняется полным gate. В facts v2 добавлены типизированные определения индексов, триггеров, прав и ограничений, без изменения общей оболочки контракта |
| Regex объявлял структурные конструкции покрытыми; README описывал legacy-проверку как допускающую публикацию | Для этих конструкций regex требует AST; документация различает извлечение операций и реконструкцию миграций. Исправлены описание legacy gate и четыре ссылки в плане |

Исполняемые проверки: [test_p2_model_review.py](wiki-doc/tests/test_p2_model_review.py)
и [test_sql_ast.py](wiki-doc/tests/test_sql_ast.py). Новые проверки проверяют
наблюдаемое поведение, в том числе согласованное изменение facts и Markdown с
перевыпуском manifest/validation; отказ не объясняется только устаревшим хэшем.

## Границы результата

Подтверждён поддержанный поднабор, а не полный PostgreSQL/Greenplum. P2-03 сохраняет
версию общей схемы 2 и уточняет типы структур; схемы и инструкции входят в хэши bundle,
поэтому прежнее решение нельзя автоматически считать проверенным новым кодом.

INDEX/TRIGGER/GRANT извлекаются как SQL-операции, но реконструкция финального состояния
миграций по manifest пока поддерживает табличные CREATE/ALTER/RENAME/DROP/COMMENT;
другие шаги дают `unsupported`. GRANT на схемы, функции и ALL TABLES IN SCHEMA
оставляет блокирующий пробел. Неустановленный межфайловый порядок не угадывается.

Это reference-цикл с проверкой сохранённых утверждений; полный LLM writer не запускался.
SQL в БД не исполнялся. Общее отсутствие регрессий P0/P1/P2-01/P2-02 проверялось
полным набором и публикационным циклом, без повторения всех прежних ручных приёмок.
