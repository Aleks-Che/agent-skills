# Повторная проверка Q-05 finalize/provenance — 2026-09-24

Проверены основной план/статус и критерии Q-05 из IMPROVEMENT-PLAN-2026-09-23.md.
Отчёт предыдущей сессии не подтвердился на успешном сценарии и контрпримерах:
наличие CLI и шести проходящих тестов не доказывало завершение цепочки.

## Найдено и исправлено

1. **Finalize обходил verify и терял подготовку.** Вызов reference `build` создавал
   другой UUID, перезаписывал inventory/plan/facts/draft/validation и маскировал
   пропущенные этапы. Runtime, SQL и DDL могли измениться после prepare.
   Теперь verify и finalize используют один read-only `verify_prepared`; полный
   manifest должен расширять подготовку с теми же UUID, tool_versions, subject,
   page_id, входами и точными хешами inventory/plan. Пропущенные артефакты не создаются.

2. **Reference-адаптер выдавался за writer/validator.** `build_bundle.py` — явно
   детерминированный адаптер для регрессий, а не оркестратор содержательной LLM-проверки.
   Finalize принимает готовые артефакты writer/validator; он не заменяет плохой текст
   reference-страницей и не переписывает отчёт с defect в ok. Это уточнение поведения
   необходимо для приёмочного требования «пропуск validation не принимается».

3. **Успешный путь не работал.** Не вызывался `publish.prepare`, без обязательного
   publication.json publisher отказывал. Даже после обхода этого отказа ответ
   completed падал с TypeError: `_result` дважды передавал publication_authorized и
   generation_completed. Теперь публикация подготавливается и привязывается к
   manifest, полный gate пересчитывается; готовность выдаётся после publisher и
   проверки результата. Изменение draft при merge требует нового validator-отчёта
   и manifest. Повтор неизменного committed-комплекта использует идемпотентность publisher.

4. **Provenance принимал отсутствующие и подменённые страницы.** Проверка наличия
   восьми ключей JSON допускала пустой каталог, неправильные типы/UUID/имена metadata,
   отсутствующие page/bundle, ручную замену текста и незавершённую публикацию.
   Новый page_provenance переиспользует схемы, evidence, gate, пути и транзакции
   publisher. Проверяются байты страницы, metadata, архив, идентичность/источники,
   текущий SQL/DDL, publication snapshot, committed journal и индекс.

5. **Не было выбора страниц для CI.** Обход только metadata не замечал legacy-
   страницу, записанную вне publisher. Теперь `provenance --page` обязателен и
   принимает несколько конкретных wiki-relative путей; выбранная legacy-страница
   отклоняется. Не выбранные audit/legacy-файлы не становятся managed автоматически.
   Обычный lint не изменён. Provenance проверяет без записи и не разрешает публикацию.
