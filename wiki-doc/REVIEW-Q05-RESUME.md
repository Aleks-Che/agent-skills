# Повторная проверка Q-05 resume — 2026-09-24

Проверены IMPLEMENTATION-PLAN.md, IMPLEMENTATION-STATUS.md и критерии Q-05.
Заявление «все критерии выполнены» не подтверждено: в статусе уже оставался
незакрытым автоматический writer/validator, а resume не выполнял частичные этапы.
Требование повторно проверять gate не делает отчёт next_stage выполнением этапа.

## Найдено и исправлено

1. **Два из четырёх исходных тестов не проверяли своё утверждение.** Они создавали
   контекст с некорректным UUID/manifest и принимали любой код из (0, 1). Verify
   отклонял такой контекст до ветки resume. Теперь используются настоящие prepare,
   строгие проверки статуса/UUID, фактической страницы и вызова реального finalize.

2. **Наличие файла считалось завершённым этапом.** Не проверялись JSON, связи,
   UUID и evidence writer/validator; coverage и manifest не участвовали в выборе.
   Порядок draft → facts также противоречил подготовке фактов до writer.
   Теперь resume проверяет все присутствующие артефакты, их схемы, идентичность,
   доказательства и покрытие. Полный существующий manifest обязан совпадать с
   подготовкой и файлами; повреждённый checkpoint не пересобирается молча.
   Список available_artifacts описывает наличие, schema_checked_artifacts —
   выполненную проверку формы/связей, а не историческое выполнение этапов.

3. **Resume не выполнял отсутствующие decision/publication.** Хотя finalize уже
   умеет их создавать, resume требовал наличия обоих файлов для вызова finalize.
   Теперь полный результат writer/validator продолжается через настоящий gate и
   publisher. При отсутствии manifest он собирается из закреплённых входов с тем
   же UUID/runtime. Перед записью повторно проверяются входы и прочитанные байты.
   Готовый decision не позволяет обойти повторный gate или validator-defect.

4. **Незавершённый writer/validator выдавал resumable с кодом успеха.** Теперь
   такой запуск возвращает needs_action, код 1, конкретный следующий артефакт и
   оба флага готовности false. Артефакты и wiki не меняются. Повреждённые данные
   возвращают blocked. Автоматический LLM-адаптер не выдумывается и не заменяется
   reference-генератором.

5. **Прерывание после publication prepare требовало отдельной обработки.**
   Существующий корректный publication.json проверяется по контракту publisher и
   привязывается к manifest без повторной подготовки. Исходные expected-хеши
   страницы/индекса сохраняются, поэтому правка редактора после снимка остаётся
   конфликтом. Для этого _check_plan умеет принять проверяемый manifest в памяти;
   обычные вызовы publisher сохраняют прежнее поведение.
