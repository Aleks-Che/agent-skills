## Замечания

### 1. [P1, P0-03] Обычный CREATE и CTAS не распознаются

Место: `scripts/sql_extract.py:45–50`, `:233–236`, `:495–501`, `:601–626`.

`CREATE_RE` требует `OR REPLACE`. Поэтому обычные `CREATE FUNCTION`, `CREATE VIEW`,
`CREATE MATERIALIZED VIEW` и `CREATE TABLE ... AS` не создают объектов.
`extract_inventory()` обходит только найденные объекты, вследствие чего исчезают и операции этих исходников.

Воспроизведение: `python -B scripts/sql_extract.py examples/10_ctas.sql` завершается с кодом **0**, но выдаёт
`items: []`, `documented_subjects: []`, `coverage_notes: []`. Такой inventory не проходит собственную схему.
Аналогично пусты примеры 02, 08 и 11; для 08 допустим ограниченный разбор, но требуется явная диагностика.

Нужно распознавать заявленные варианты объявлений и поддержанные операции вне routines либо регистрировать конкретный пробел разбора. Пустой недопустимый результат не должен считаться успешным.

### 2. [P1, P0-03] Частичный разбор не создаёт обязательства проверки пробела

Место: `scripts/sql_extract.py:302–305`, `:516–523`, `:542–549`; `scripts/validation_plan.py:52–86`, `:123–131`.

Тело с тегом `$body$` пропускается полностью: извлечение тела ищет только `$$`,
после чего сканирование операций считает tagged body строкой.
`TRUNCATE` внутри функции с обычным `$$` также исчезает без `coverage_notes`.
Для функции с `TRUNCATE demo.t; PERFORM demo.log();` остаётся только `PERFORM`, а примечаний нет.
Это случай неполного непустого inventory, поэтому одной проверки `minItems` недостаточно.
Добавление `TRUNCATE demo.t;` перед `PERFORM demo.log();` вообще не меняет сгенерированный план:
сравнение двух словарей планов возвращает True.

Диагностика неизвестного синтаксиса ограничена пятью словами `TRIGGER/INDEX/CONSTRAINT/GRANT/REVOKE`.
Даже когда примечание создано, генератор плана вообще не читает `coverage_notes` и не создаёт для него блокирующего обязательства.
`EXECUTE` фиксируется только как `dynamic target`: вид команды, шаблон цели и границы реально разобранного выражения не сохраняются.

Нужно учитывать покрытие каждого исполняемого фрагмента, различать неизвестное runtime-имя и неразобранный код, а последний переносить в план как обязательную проверку с возможным `inconclusive`.
Это прямо входит в приёмку P0-03, а не только в расширение парсера P1-03.

### 3. [P1, P0-03] Комментарии и строки создают ложные операции; координаты исходника смещены

Место: `scripts/sql_extract.py:111–170`, `:233–236`, `:304–316`, `:530–538`.

`extract_objects()` ищет CREATE в сыром SQL. Затем обрезка исходника по найденному CREATE удаляет маркер комментария или открывающую кавычку.
Например, исходник из одной строки `-- CREATE OR REPLACE VIEW demo.fake AS SELECT * FROM demo.secret;`
создаёт документируемый объект `fake` и операцию `SELECT`. Аналогично обрабатывается строковый литерал с текстом CREATE.
Штатные тесты вызывают `extract_operations()` отдельно и этот путь не проверяют.

Очистка удаляет символы, но позиции совпадений в укороченном тексте используются как позиции исходного текста.
Дополнительно для тела routine не прибавляется смещение от начала файла.
В примере 01 `INSERT` реально находится на строке 4, а `SELECT` — на строке 5; inventory указывает 3 и 4 соответственно, причём диапазоны всегда однострочные.
Для `-- first line comment\nSELECT 1;\nSELECT 2;` обе операции получают строку 1 вместо 2 и 3.
Диапазоны dollar-quoted строк рассчитаны по неочищенному тексту: после длинного комментария внутренний `SELECT` из `$$ SELECT 999; $$` становится лишней операцией.
Вложенный комментарий `/* outer /* inner */ SELECT 0; */ SELECT 1;` также даёт два SELECT.

Нужен единый лексический проход с сохранением координат, границ строк и вложенных комментариев; объявления следует искать только в исполняемом коде.

### 4. [P1, P0-03] Объекты получают чужие тела, а выбранная граница страницы не применяется

Место: `scripts/sql_extract.py:501–538`, `:558`; `scripts/validation_plan.py:104–111`, `:123–128`.

Поиск `$$` не ограничен текущим объявлением. Если за view следует функция, view получает тело этой функции.
Для `CREATE OR REPLACE VIEW demo.v AS SELECT id FROM demo.view_source;` с последующей функцией,
читающей `demo.function_source`, обе операции inventory читают `demo.function_source`; зависимость view потеряна.
Существующий пример 09 имеет именно такой порядок объектов, но одинаковая таблица-источник скрывает ошибку в штатном тесте.

Повторный поиск начала объявления использует только имя, поэтому перегрузки одной функции получают тело первого объявления.
В примере 06 `documented_subjects` дополнительно превращается в три одинаковых `orders_summary`, что нарушает `uniqueItems` схемы.
Полная каноникализация относится к P1, но независимая идентичность выбранных объявлений нужна уже P0-03.

`documented_subjects=['a']` меняет только поле результата: для файла с view `a` и `b` inventory и план содержат операции обоих.
Генератор использует первый subject как ключ всей страницы. Это не отделяет контекст от документируемых объектов.

Нужно передавать найденные границы объявлений напрямую, сохранять различимость объектов и формировать обязательства в пределах выбранной страницы.

### 5. [P1, P0-02/P0-03] Автоопределение типа и конкретные содержательные обязательства не работают

Место: `scripts/validation_plan.py:23–49`, `:61–85`; `scripts/check_policy.py:190–207`, `:233–261`.

Определение типа ищет `CREATE_VIEW`, `CREATE_MATERIALIZED_VIEW`, `CREATE_TABLE_AS` или `details.object_kind`,
но экстрактор ничего из этого в inventory не записывает. Поэтому обычный распознанный view получает тип `function`,
проверку сигнатуры и не получает проверку колонок. Ручной `--kind` обходит этот конкретный дефект, но не исправляет автоматический режим.

Для `CREATE OR REPLACE VIEW demo.v AS SELECT price * quantity AS total FROM demo.t WHERE status = 1;`
план не содержит ни `formula`, ни `condition`.
Флаги `has_formula`/`has_condition` никогда не создаются экстрактором; даты и активный профиль не входят в построенный контекст.
Сигнатуры остаются во внутренних `ObjectInfo`/текстовом scope и не передаются как структурированные данные объявления.
CTE и TEMP TABLE есть в inventory, но `derive_inventory_checks()` не формирует для них отдельных обязательств.

Даже при ручной установке контекста `has_formulas=True`, `has_conditions=True`, `profile_active=True`
получаются общие предметы `.../formula/`, `.../condition/`, `.../profile/` с пустым конкретным ID.
Это не требуемое раскрытие всех формул, условий и требований профиля в отдельные обязательства.

Нужно сохранять тип/сигнатуру объявлений и конкретные предметы анализа, а затем выводить проверки из них.
Сложные выражения могут быть неподдержанными, но тогда необходима явная проверка пробела вместо исчезновения из плана.

### 6. [P1, P0-02/P0-03] Генератор выдаёт план, нарушающий контракт, и подавляет собственные ошибки

Место: `scripts/check_policy.py:190–210`; `scripts/validation_plan.py:150–159`.

Для `examples/07_dynamic_sql.sql` генерируется проверка:

```json
{"id":"unknown","rule_id":"unknown","subject":"fn_dynamic/unknown/","source":"inventory","applicable":true,"blocking":false,"category":"technical"}
```

У неё отсутствует обязательный `inventory_anchor`. `validation_plan.schema.json` отклоняет план:
`required_checks[5]: 'inventory_anchor' is a required property`.
Та же проблема возникает у общих проверок formula/condition при истинных соответствующих флагах.

`validate_check_against_policy()` уже обнаруживает отсутствие якоря, но `generate_plan()` собирает ошибки и выполняет `pass`.
Вопреки комментарию, ошибки даже не журналируются. Входной inventory также не проверяется против схемы перед генерацией.

Нужно формировать полноценные проверки с существующими якорями и завершать генерацию диагностикой при нарушении контракта.

### 7. [P1, P0-02/P0-03] При переносе в план независимые якоря подменяются

Место: `scripts/check_policy.py:238–257`; `scripts/validation_plan.py:139–146`; `scripts/sql_extract.py:499`.

`derive_inventory_checks()` заново нумерует операции по виду во всём списке, игнорируя `anchor.ordinal`.
Путь берётся из `anchor.path`, хотя по inventory-схеме он находится в `source_ref.path`.
Генератор затем подставляет путь первого входного файла для всех операций.

Для валидного inventory с `a.sql / function+demo+a() / SELECT / 1` и
`b.sql / function+demo+b() / SELECT / 1` второй якорь плана становится
`a.sql / function+demo+b() / SELECT / 2`. Такой ссылки нет в inventory; проверка связности P0-01 её отклоняет.
Подтверждённый результат `_linked_artifacts()`: `validation_plan: required_checks.6.inventory_anchor: unknown source anchor`.
Сам экстрактор тоже использует общие счётчики между объектами вместо номеров внутри области.

Нужно сохранять исходные `path`, `object_or_scope`, `construct`, `ordinal` без перенумерации,
а уникальный ID проверки строить с учётом полного якоря.

### 8. [P1, P0-03] Операции MERGE и зависимости DML искажаются

Место: `scripts/sql_extract.py:62`, `:337–364`, `:471–486`.

`WHEN MATCHED THEN UPDATE SET ...` внутри MERGE создаёт дополнительный самостоятельный UPDATE с `writes=['SET']`.
Это воспроизводится на примере 04: две записи UPDATE вместо одной самостоятельной операции, MERGE и двух вызовов PERFORM.
Если действия MERGE сохраняются отдельно, их цель должна оставаться целью MERGE, а не словом SET.

`_extract_from_joins()` просматривает следующие 2000 символов, не ограничиваясь оператором:
`SELECT * FROM demo.a; SELECT * FROM demo.b;` приписывает первому SELECT обе таблицы,
причём имена содержат завершающий `;`.
`DELETE FROM demo.t USING demo.s WHERE demo.t.id=demo.s.id;` не сохраняет чтение `demo.s`.

Нужны границы операторов, корректная обработка действий MERGE и извлечение зависимостей поддержанных DML.
Если конкретная форма не поддерживается, это должно отражаться как пробел разбора.

### 9. [P1, P0-02] Политика не защищает критичность и применимость проверки

Место: `scripts/check_policy.py:266–307`.

`validate_check_against_policy()` принимает проверку `identity` с
`category='editorial'`, `blocking=False`, `applicable=False` и возвращает `[]`.
Проверяются только допустимые значения category/source и наличие якоря, но не соответствие правилу, предмету и контексту.
Аргумент `object_kind` не используется; обоснование `not_applicable` не проверяется.

`is_defect_blocking()` — отдельный работающий помощник для известных строковых кодов,
но он не получает `rule_id`/предмет проверки, а неизвестному коду доверяет `declared_blocking`.
Поэтому он сам по себе не реализует требование вычислять критичность по правилу и предмету.

Интеграция с полным gate действительно запланирована на P0-05. Её отсутствие не считается новой регрессией старого gate,
но не позволяет объявить выполненной приёмку P0-02 «технический дефект нельзя сделать редакционным».
До интеграции нужно обеспечить такое поведение самого движка политики и проверить необоснованную неприменимость найденной операции.
Отдельного проверенного пути для честно описанного отсутствия DDL и различения дефекта SQL/документации также нет.

### 10. [P2, P0-02] Применимость секций расходится с template.md

Место: `references/check-policy.json:233–250`; `scripts/check_policy.py:80–123`; `scripts/validation_plan.py:85`.

- `formulas_dependencies` требует `has_formulas=True`. При `object_kind='view', has_reads=True, has_formulas=False`
  блок 04 отсутствует, хотя template.md требует зависимости для всех объектов, включая явное отсутствие зависимостей.
- `_or` с булевыми значениями проверяет сами значения политики, а не соответствующие поля контекста:
  `_evaluate_condition({'_or': {'has_reads': True, 'has_writes': True}}, {'has_reads': False, 'has_writes': False})` возвращает True.
- Условие `source_count_gte` читается как точное имя поля и не реализует сравнение `>=`.
  Контекст с `source_count=2` или 3 не включает диаграмму. Кроме того, генератор считает число входных файлов,
  тогда как шаблон говорит о физических источниках или сложном потоке изменений.
- Блок entities ограничен таблицами/view/CTAS и не учитывает RETURNS TABLE, явно указанный в шаблоне.

Нужно согласовать модель условий и контекст с текстовой картой, добавить автоматическую проверку соответствия.
Текущие тесты секций покрывают только включение header, signature и entities в простейших случаях.
