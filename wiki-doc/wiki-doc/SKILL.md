# Wiki-документация SQL

Объясняй назначение, структуру, вычисления и движение данных с опорой на исходники.
Технические факты подтверждай SQL/DDL; бизнес-интерпретации отделяй от подтверждённых
описаний. Недостающие сведения обозначай явно. Не исполняй документируемый SQL:
примеры вызова создаются как текст, а выполнение требует отдельного запроса.

## Контекст и режим

1. Определи границы SQL-проекта, wiki, индекс и соглашения ссылок. Сохраняй существующий
   формат ссылок; для новой Markdown-wiki используй относительные Markdown-ссылки.
2. Определи диалект, версию СУБД и документируемую ревизию из проекта. Если версия
   не установлена, записывай `unknown`; не заявляй совместимость неподтверждённых конструкций.
3. Прочитай [профиль проекта](project-profile.md) только при совпадении его области
   применения. Для CKR_GP дополнительно используй [правила доступа](rules.md).
   Наличие этих файлов в пакете само по себе не включает профиль для любого проекта.
4. Выбери режим: генерация/обновление страницы, Query или Lint. Для генерации
   применимость секций задаётся исключительно [template.md](template.md).

Пример обращения: «Документируй path/to/object.sql в docs/wiki».
Если файл содержит несколько объектов, сначала составь их список. Создай отдельные
страницы объектов; для миграции можно создать страницу изменений со ссылками на объекты.
Не приравнивай файл, INSERT, таблицу и бизнес-сущность друг к другу.

## Генерация и обновление

### 1. Инвентаризация и поиск определений

Прочитай исходный SQL. Различай выполняемые операторы, комментарии, строковые литералы,
тела функций и динамические команды. Зафиксируй все операции, ветвления и зависимости,
включая чтения через `MERGE USING`, `UPDATE FROM`, `DELETE USING`, подзапросы,
CTE, CTAS, вызовы через SELECT/PERFORM/CALL и выражения.

Для объединения **читаемых и изменяемых объектов** получи определения по
[ddl-finder.md](ddl-finder.md). Включай цели, даже если они нигде не читаются.
Для view, временной таблицы и CTAS используй определение в исходном SQL.
CTE и алиас не являются самостоятельными физическими таблицами.
Для вызываемых функций найди объявление, если оно нужно для сигнатуры, типов или
объяснения эффекта; неподтверждённый эффект вызова не выдумывай.

Можно делегировать поиск независимых объектов субагентам с инструкцией ddl-finder.
При отсутствии делегирования выполни **тот же алгоритм** самостоятельно:
поиск по имени, обязательный поиск всех определений/изменений по содержимому,
разрешение версии. Отдельного сокращённого fallback нет.

### 2. Реестр фактов и идентификация

Построй реестр по контракту [references/facts.md](references/facts.md) версии 2.
Схема: `schemas/facts.schema.json`. Каждый реестр содержит `schema_version: 2` и
`run_id` (UUID запуска). Все артефакты одного цикла должны совпадать по `run_id`.

Сверь его операции с SQL до генерации текста. Для нескольких объектов файла общий
анализ можно выполнить один раз, затем выделить срез для каждой страницы с явным
`documented_object_ids`. Определения из контекста не становятся автоматически
объектами документирования. Writer использует факты повторно; обнаруженная ошибка
исправляется в реестре с обновлением затронутых блоков.

Уникальные ID фактов, например: `op_NNN` (операции), `col_NNN` (колонки), `formula_NNN`
(формулы), `cond_NNN` (условия), `unknown_NNN` (неопределённости). Общая область ID
включает также объекты и определения; формат префикса не обязателен. ID стабильны
между блоками одной генерации; при изменении SQL перестрой затронутые факты и покрытие.

Вычисли постоянный `page_id` по правилам ниже. **Для каждой страницы отдельно** создай
уникальную директорию `<wiki_output_dir>/.tmp/<run_id>/`, где `run_id` — UUID.
Один run содержит артефакты одной страницы; следующие этапы выполняются для неё.
Сохрани туда `facts.json`, исходные хеши документов и индексируемой страницы,
если они уже существуют. Для нового файла фиксируй его отсутствие.

### 3. Генерация применимых блоков

Прочитай карту секций [template.md](template.md). Для каждого применимого блока
используй [doc-writer.md](doc-writer.md) самостоятельно либо передай эти инструкции
субагенту. Контракт входа одинаков:

- путь к SQL и его ревизия/хеш;
- нужный срез реестра и определения SQL/DDL с путями и диапазонами строк;
- файл шаблона блока;
- применимые секции и активный профиль;
- окончательный путь страницы для построения относительных ссылок;
- при необходимости краткие результаты связанных блоков.

Не дублируй полный SQL и все DDL в каждом запросе: файлы доступны по путям,
нужные фрагменты можно дочитать. Сохраняй `block_N.md` и карту
`coverage_N.json` внутри директории запуска. Один агент может написать несколько
блоков небольшой страницы; шесть отдельных вызовов не обязательны.

Собери применимые блоки в `.tmp/<run_id>/page.draft.md`, объедини карты покрытия
в `coverage.json` версии 2 (схема: `schemas/coverage.schema.json`). Карта покрытия —
обёртка с `schema_version`, `run_id`, `page_id` и `entries` (маппинг fact_id → секции).
На этом этапе основная страница и индекс ещё не изменяются.

### 4. Валидация черновика

Передай [doc-validator.md](doc-validator.md):

- пути к черновику, **полному** реестру и карте покрытия;
- исходные SQL и все найденные определения/миграции DDL с хешами и порядком применения;
- [template.md](template.md), использованные блоки, активный профиль и правила;
- `page_id`, пути основной страницы/индекса и их исходные хеши.

Валидатор сначала независимо сверяет **SQL → реестр**, затем
**SQL/DDL + реестр → документация**. Критерий готовности определён только в
doc-validator; процент сам по себе не разрешает публикацию.

После сохранения отчёта проверь доступные артефакты версии 2:
`python scripts/artifact_schema.py <run_dir> --artifacts facts coverage validation`.
Если уже созданы план или другие артефакты, они тоже проверяются. Ошибки формы и
ссылок исправляются до публикации. Контракт и переход со старого формата — в
[references/artifacts.md](references/artifacts.md).

При `revise` исправь факты/черновик и повтори затронутые проверки. Всего не более
трёх запусков валидатора на одну попытку генерации. При `blocked` или после третьего
неуспешного запуска сохрани черновик и отчёт, сообщи конкретные нерешённые вопросы.
Не меняй основную страницу и не запускай новый цикл перегенерации автоматически.

### 5. Публикация в локальную wiki

Только после содержательной проверки с результатом `ready` и успешной проверки
структуры/связности доступных артефактов. `valid: true` от `artifact_schema.py`
и `ready` от старого расчётчика по отдельному отчёту сами по себе недостаточны:

1. Проверь, что SQL/DDL, основная страница и индекс не изменились с момента чтения.
   При изменении исходников обнови реестр и валидацию; при конфликте wiki согласуй
   изменения с текущим содержимым, сохраняя ручные правки.
2. Подготовь новую страницу и индекс с сохранением существующих ссылок. Восстановление
   после ошибки должно сохранять прежние файлы: держи их копии в директории запуска.
3. Перед заменой сериализуй запись в этот индекс средствами среды (эксклюзивная
   блокировка/один основной агент) и повторно проверь хеши. Отдельные run_id не защищают
   общий индекс от одновременной записи. При невозможности исключить конфликт оставь черновик.
4. Замени основную страницу подготовленным файлом, затем обнови индекс.
   При частичной ошибке восстанови изменённые этим запуском файлы из копий.
5. Убедись, что страница и ссылка в индексе существуют. После успеха очисти только
   свою директорию запуска; перед рекурсивным удалением проверь её абсолютный путь.

Запрос на обновление wiki разрешает обычную замену сгенерированной страницы:
повторное подтверждение на каждую перезапись не требуется. Если ручной текст
конфликтует с новым содержимым и намерение неясно, оставь черновик с конкретным конфликтом.
Размещение на внешнем сервисе не входит в этот локальный шаг.

## Идентификатор страницы

Храни канонический ключ объекта отдельно от имени файла:

- relation: `kind + schema + name`;
- function/procedure: дополнительно **всегда** упорядоченные типы входных аргументов,
  включая INOUT/VARIADIC; имена параметров, DEFAULT и OUT-параметры не входят в ключ;
- migration: путь относительно SQL-проекта и идентификатор миграции из проекта.

Учитывай регистр quoted identifiers; не своди разные схемы или типы к одному ключу.
Для файлов используй безопасный короткий slug и суффикс хеша канонического ключа,
например `fn-core-calc--<hash>.md`. Используй стабильный алгоритм SHA-256
(начни с 12 hex-символов); при коллизии разных ключей увеличь длину.
Замена пунктуации в slug не влияет на уникальность, поскольку хеш берётся от исходного ключа.

У существующей страницы сохраняй путь, если её ключ однозначно установлен.
Неразрешённая схема или сигнатура — неопределённая идентичность: черновик можно создать,
финальную страницу не публикуй до разрешения ключа.

## Query

Найди релевантные страницы через индекс. Ответь со ссылками на страницы и при
необходимости исходный SQL. Если wiki расходится с кодом, явно укажи расхождение.
Не сохраняй новый анализ без запроса пользователя.

## Lint

Проверь разрешение ссылок, отсутствующие/дублирующиеся ключи страниц, актуальность
SQL/DDL-хешей, противоречия коду и применимые секции. Проверки доступа включай только
для активного профиля. Изолированные страницы оценивай по назначению, а не автоматически
как ошибку. По запросу проверки возвращай отчёт; исправляй при запросе на исправление.

## Проверка скилла после изменений

Используй контрольные случаи и порядок проверки из [examples/README.md](examples/README.md).
Проверяй фактические операции, типы, условия и решение о публикации, а не совпадение
формулировок с эталоном.

### Валидация артефактов

Установи зависимости: `python -m pip install -r requirements.txt`.
Для проверки полного комплекта артефактов используй:

```text
python scripts/artifact_schema.py <artifacts_dir>
```

По умолчанию обязательны все семь артефактов. Для промежуточного этапа явно укажи,
например, `--artifacts facts coverage`; незавершённый комплект не выдаётся за полный.
Код 0 — форма и связи проверены, 1 — ошибка контракта, 2 — ошибка чтения/JSON,
зависимостей или CLI. Результат всегда содержит `publication_authorized: false`.
Правила ссылок, отдельная проверка manifest миграций и ограничения P0-01 описаны
в [references/artifacts.md](references/artifacts.md).

### Независимый SQL-инвентарь и план проверок

Для независимого анализа SQL без чтения facts.json:

```text
python scripts/sql_extract.py <sql_file> --dialect postgres --subjects <names>
python scripts/validation_plan.py <inventory.json> --kind function --policy references/check-policy.json
```

Экстрактор (`scripts/sql_extract.py`) извлекает:
- CREATE FUNCTION/PROCEDURE/VIEW/MATERIALIZED VIEW/TABLE AS
- DML: SELECT, INSERT, UPDATE, DELETE, MERGE
- PL/pgSQL: PERFORM, CALL, EXECUTE
- CTE, TEMP TABLE, FROM/JOIN зависимости
- Dollar-quoted тела функций

**Ограничения:** regex-based, не полный AST. Dynamic имена не разрешаются.
Неподдержанный синтаксис фиксируется в `coverage_notes`. Подробнее — в
заголовке `sql_extract.py`.

Генератор плана (`scripts/validation_plan.py`) объединяет inventory с
`check-policy.json` и формирует `validation_plan.json` с конкретными
обязательными проверками.

### Схемы артефактов (версия 2)

| Артефакт | Схема | Описание |
|----------|-------|----------|
| facts.json | `schemas/facts.schema.json` | Реестр фактов с run_id |
| coverage.json | `schemas/coverage.schema.json` | Карта покрытия (обёртка) |
| validation.json | `schemas/validation.schema.json` | Отчёт валидации |
| validation_plan.json | `schemas/validation_plan.schema.json` | План проверок |
| manifest.json | `schemas/manifest.schema.json` | Манифест запуска |
| inventory.json | `schemas/inventory.schema.json` | Независимый инвентарь SQL |
| decision.json | `schemas/decision.schema.json` | Решение о публикации |

Все артефакты v2 содержат `schema_version: 2` и `run_id` (UUID).
Манифест миграций (`examples/migrations/manifest.json`) — отдельная схема
`schemas/migration_manifest.schema.json`.
