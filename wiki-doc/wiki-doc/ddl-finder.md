# Поиск определений SQL

Вход: корень SQL-проекта, объект со схемой/типом, выбранная ревизия, диалект,
активный профиль и при наличии порядок миграций. Только читай файлы.
Алгоритм одинаков для субагента и основного агента.

## 1. Найди кандидатов

Поиск по имени файла — ускорение, а не условие полноты. Используй доступный поиск
файлов, затем поиск по содержимому (например rg), экранируя искомые идентификаторы.

1. Найди файлы с именем объекта. При активном CKR_GP можно начать с loader,
   `gp/all/` и `001create_table/`; это необязательные соглашения профиля.
2. **Независимо от результата** найди по содержимому проекта определения и изменения
   объекта: CREATE TABLE/VIEW/MATERIALIZED VIEW/FUNCTION/PROCEDURE, CTAS, ALTER,
   COMMENT, DROP/RENAME, CREATE INDEX/TRIGGER, GRANT/REVOKE и относящиеся к нему
   ограничения/индексы.
3. Обработай quoting, CREATE OR REPLACE, IF NOT EXISTS и search_path. Подтверждай
   совпадение схемы и типа по SQL, а не по имени файла. Если схема зависит от
   неизвестного search_path, сохрани кандидатов как неоднозначные.
4. Проверь определения в самом документируемом файле, в миграциях и подключаемых
   файлах сборки. Не ограничивай поиск директорией loader или названием migrations.
5. Различай активные определения, архивы, тесты, uninstall/down-миграции. Их наличие
   не означает, что все они применяются к одной версии. Основание выбора зафиксируй.

Для view/CTAS извлекай выходные колонки и выражения. Для типов их исходных колонок
при необходимости разрешай определения зависимостей; отслеживай посещённые объекты,
чтобы циклические ссылки не вызывали бесконечный поиск.

## 2. Восстанови нужную версию

Сначала установи, что документируется: снимок схемы или состояние после конкретного
набора миграций. Порядок бери из manifest/changelog/сборки или явно установленного
соглашения проекта. Даты/номера в имени допустимы только при таком соглашении.
Время изменения файла, порядок glob и время checkout не задают порядок миграций.

При известном порядке последовательно применяй изменения к модели метаданных:
ADD добавляет, DROP удаляет, RENAME переносит имя, ALTER TYPE/DEFAULT/NULLABILITY
заменяет соответствующий атрибут. Обновляй комментарии и ограничения.
Не объединяй списки колонок разных состояний.

Если порядок, ветка или целевая ревизия неизвестны, верни варианты и неопределённость.
Не объявляй одно из определений актуальным без основания.
Неоднозначность можно разрешить из конфигурации проекта; если это невозможно,
передай основному агенту конкретный недостающий факт, сохранив найденные данные.

## 3. Статус и результат

| Статус | Значение |
|--------|----------|
| resolved | Определение или последовательность миграций однозначно даёт структуру на указанную ревизию |
| not_found | Выполнен поиск, определения нет; внешнее происхождение не установлено |
| ambiguous | Есть несовместимые кандидаты, неизвестная схема или порядок изменений |
| external | Конфигурация/документация явно подтверждает управление объектом вне проекта; укажи доказательство |

Несколько файлов CREATE + ALTER с известным порядком могут давать resolved.
Одно упоминание имени в SELECT не доказывает external.

Верни объект, статус, список просмотренных определений с путями/строками, выбранную
ревизию и порядок миграций с основанием. Для resolved добавь таблицу:

| Колонка | Тип | NULL | DEFAULT | Комментарий | Основание |
|---------|-----|------|---------|-------------|-----------|

Отдельно перечисли ключи, ограничения, индексы, распределение, выходные выражения
для view/CTAS и изменения по миграциям. Для ambiguous не смешивай варианты;
для not_found/external перечисли подтверждённые сведения и неизвестные поля.
Не копируй полный DDL в ответ и не угадывай недостающие типы.
