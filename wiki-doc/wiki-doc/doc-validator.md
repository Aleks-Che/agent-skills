# Валидация документации

Вход: черновик, полный реестр, карта покрытия, исходные SQL/DDL/миграции с хешами
и порядком применения, [template.md](template.md), использованные блоки, активный
профиль и правила, run_id, page_id и пути страницы/индекса с исходными хешами.

Не исправляй файлы. Верни отчёт и список конкретных исправлений.
Если реестр отсутствует, запроси его у основного агента: старый подсчёт INSERT
не заменяет проверку покрытия.

## Проверка применимости

Определи тип объекта и реально присутствующие конструкции. Используй исключительно
[карту секций](template.md): формула в view, read-only функции или SELECT внутри
миграции проверяется так же, как формула в ETL.
Отсутствие данных для проверки не означает not_applicable.

Активируй профиль только по его признакам проекта. Проверки CKR_GP не распространяются
на произвольную функцию. Профиль не отключает проверку существующей бизнес-логики.

## Порядок проверки

### 1. Независимая сверка SQL → реестр

Прочитай исходные SQL, не ограничиваясь пересказом writer или списком из реестра.
Проверь соответствие хешей и ревизии. Область страницы задаётся documented_object_ids:
проверяй операции этих объектов и заявленные эффекты их вызовов, не требуй описывать
все определения вспомогательного context.sql. Для каждого реального оператора в этой области проверь наличие
в реестре с правильной областью видимости, порядком, reads/writes/calls и условиями.
Включи UPDATE FROM, DELETE USING, MERGE USING, CTAS, CTE, выражения, вызовы и динамический SQL.
Для TRIGGER/INDEX/GRANT/REVOKE и ограничений CREATE/ALTER сверяй также все поля
`operations.structure` версии `extension_version: 1`, включая полный DDL.
Каждое обязательство `trigger`, `index`, `constraint`, `access_rule` должно иметь
результат с `fact_ids` соответствующей операции; поля описаны в
[references/facts.md](references/facts.md).
Не засчитывай комментарии или текст внутри неисполняемой строки как отдельную операцию.
Проверь и обратное: в реестре нет вымышленных операций.

Сверь восстановление DDL по выбранному порядку миграций, включая DROP/RENAME/TYPE.
Проверь DDL как источников, так и целей; файл, найденный по имени, не подтверждает
сам по себе схему, ревизию или актуальность.
Расхождение SQL и реестра — дефект, даже если документация точно повторяет реестр.

### 2. Сверка SQL/DDL + реестр → страница

Для каждого применимого факта проверь содержание, а не только заголовок или запись
в coverage.json. Обязательные проверки общего уровня имеют ID
`identity`, `sql_registry`, `registry_document` и не могут быть not_applicable.

Запусти `coverage_gate.py --bundle <run_dir> --wiki-root <wiki_dir> --json` по
[контракту покрытия](references/coverage.md). Для ссылок на SQL вне wiki добавь
`--link-root <project_dir>`. Разрешённые диапазоны `fragments` указывают текст,
который нужно сопоставить с фактом и исходником. При неверном непустом тексте
зафиксируй предметный defect с fact_ids и доказательствами из SQL и черновика;
успех проверки адреса фрагмента не означает успех содержательной проверки.

| Группа | Что проверять |
|--------|---------------|
| Идентичность | Канонический ключ, схема/имя/тип, сигнатура входных типов, page_id и ссылки на ревизию |
| Структура | Только применимые секции; соответствие форматов таблицам блоков |
| Сигнатура | IN/OUT/INOUT/VARIADIC, типы, RETURNS, DEFAULT из объявления, атрибуты и корректные примеры вызова |
| Колонки | Тип цели/результата и тип выражения отдельно, NULL/DEFAULT/ограничения, доказательства из правильной версии DDL |
| Формулы | Арифметика, CASE и порядок ветвей, агрегаты, окна, приведения, NULL и точные значения; любой тип объекта |
| Условия | JOIN-ключи, WHERE/HAVING, границы дат, IF/циклы, дедубликация и ограничения числа строк |
| Зависимости | Все читаемые/изменяемые объекты и вызовы, включая USING; CTE/temp отделены от внешних объектов |
| Эффекты | Порядок и область изменений, переход структуры миграции, реальные ошибки/обработчики; никаких домыслов о транзакциях |
| Диаграмма | Узлы и направления соответствуют фактическим операциям; UPDATE/MERGE/CTAS не теряются |
| Проект | Правила только активного профиля; прямой audit-вызов отличается от чтения таблиц аудита |
| Неопределённости | Нет неподтверждённых утверждений, ограничения и unknown явно описаны с влиянием |
| Примеры/ссылки | Реальные аргументы и объекты, существующие ссылки; примеры не выполняются при ревью |

Относительные ссылки черновика проверяй относительно окончательного пути страницы,
а не `.tmp/<run_id>/`; проверь также ссылки подготовленного индекса на будущую страницу.

Проверяй Mermaid доступным инструментом, если он есть. Если рендерер недоступен,
сообщи это как ограничение проверки; не заявляй инструментальную проверку рендеринга.
Смысловые направления связей всё равно проверяются по SQL.

### 3. Отчёт и решение

Верни Markdown-отчёт с дефектами (страница/секция, что написано, что в SQL/DDL,
пути/строки, исправление) и JSON версии 2 по
[schemas/validation.schema.json](schemas/validation.schema.json).
run_id/page_id возьми из запуска, не создавай новые. Пример формы:

```json
{
  "schema_version": 2,
  "run_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "page_id": "<page_id из запуска>",
  "checks": [{
    "id": "review-operation-1",
    "plan_check_id": "<required_checks[].id из плана>",
    "fact_ids": ["op_001"],
    "status": "ok",
    "blocking": true,
    "category": "technical",
    "reason": "Операция сопоставлена исходнику, реестру и странице",
    "evidence": [{
      "root": "project", "path": "sql/object.sql",
      "start_line": 3, "end_line": 5,
      "sha256": "<SHA-256 байтов реально прочитанного файла>"
    }]
  }]
}
```

Это фрагмент формы отчёта: подставь реальные UUID, хэш, ID и полный набор результатов
по сохранённому плану. Не используй пример как готовый валидный артефакт.

Дай ровно один результат на каждую проверку из validation_plan.json. Для предметных
операций, каждой формулы, каждого условия и неизвестных целей укажи связанные
fact_ids. Копируй сгенерированные ID; они зависят от полного SQL-якоря, а не только
от номера операции. Не своди несколько выражений к общей строке «формулы проверены».
ID уникальны; один факт не считается несколько раз за счёт сводных строк.
Для not_applicable укажи причину, для inconclusive — недостающие данные.
Для ok/defect evidence должен содержать хотя бы одну непустую ссылку;
для inconclusive/not_applicable допустим пустой массив. Используй структурированные
ссылки root/path/start_line/end_line/sha256; строки оставлены только для старой диагностики.
Обязательный `plan_check_id` ссылается на `required_checks[].id`. Самостоятельно найденные дефекты могут не иметь этой ссылки.
Не записывай итоговый decision внутрь validation.json: отчёт и решение — разные артефакты.

| Статус | Значение |
|--------|----------|
| ok | Содержательное утверждение проверено и верно |
| defect | Установлено расхождение |
| inconclusive | Проверка применима, но её результат не установлен |
| not_applicable | В исходнике нет соответствующей конструкции/требования |

`blocking: true` ставь для технических ошибок: неверные типы, формулы, даты,
сигнатуры, зависимости, пропуски/выдумывание операций, нарушенная идентичность,
неподтверждённые факты, а также неточное описание применимого правила доступа.
Правильно описанное нарушение **в исходном SQL** не является ошибкой документации:
отрази его отдельно как замечание к коду, не требуй изменять SQL ради публикации страницы.
Неблокирующий defect допустим только для редакционного улучшения, которое не меняет факты.
Для дополнительного редакционного замечания нужен defect_code из
blocking_override_rules.editorial_defect_codes политики. Неизвестный код при defect
блокирует; одной пометки category: editorial недостаточно.

Отсутствие DDL можно честно описать как unknown: проверка корректности такого
ограничения может быть ok. Это не то же самое, что inconclusive-проверка опубликованного
конкретного типа без основания. Неизвестный ключ объекта остаётся блокирующим.

## Единый критерий готовности

Счётчики: O = ok, D = defect, I = inconclusive. not_applicable исключается.

- Покрытие проверок: `100 * (O + D) / (O + D + I)`.
- Доля верных результатов: `100 * O / (O + D)`.
- При нулевом знаменателе метрика не определена и ready недопустим.
- `ready`: покрытие = 100%, доля верных ≥ 85%, нет blocking defect/inconclusive.
  Все оставшиеся неблокирующие замечания перечислены в отчёте.
- `blocked`: есть blocking inconclusive — требуются исходные сведения.
- `revise`: остальные случаи, в том числе неблокирующая неопределённость.

Основной агент создаёт manifest и выполняет полный gate:
`python scripts/validation_gate.py --bundle <run_dir> --root project <project_dir> --root wiki <wiki_dir> --write-decision --json`.
Готовое решение проверяется той же командой без `--write-decision`. Gate проверяет
контракты, реальные доказательства и хэши, пересчитывает SQL-инвентарь и план,
проверяет покрытие и считает только обязательные результаты. Техническую критичность
задаёт policy; `blocking: false` или категория в отчёте не снижают её.
Дополнительные успешные строки не повышают метрики; дополнительные технические дефекты
блокируют. Найденная применимая операция не может стать not_applicable.
Без Python/зависимостей сохрани черновик и ограничение; ручная оценка не даёт допуск.

Основной агент сохраняет отчёт рядом с черновиком. Не более трёх запусков валидатора
на попытку генерации; публикация и остановка выполняются по [SKILL.md](SKILL.md).

## Дополнительные механизмы P1

Проверяй черновик после `publish.py prepare`, уже с сохранёнными ручными блоками.
`publication.json` включается в manifest; неподготовленная или изменившаяся страница
не публикуется. Порядок: [publication.md](references/publication.md).

Gate независимо сверяет параметры/RETURNS, структурные назначения/ветви операций,
доступные типы колонок и выражений, значения контролируемых таблиц `claims-v1` и
наблюдения активного профиля. Ограничения AST/вывода типов —
[sql-support.md](references/sql-support.md). Проверка произвольного текста, логики
пояснений и смысловых рёбер диаграммы остаётся отдельным содержательным проходом.
Не считай JSON-sidecar доказательством содержимого Markdown.

После изменения инструкций выполняется [регрессия](references/regression.md):
11 случаев, все 14 предметов, минимум три повторения, раздельные текстовые и согласованные
мутации. Отсутствующий агентный прогон отражается явно; reference adapter не является LLM.
