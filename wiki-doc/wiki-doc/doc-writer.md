# Генерация блока документации

Для примеров вызова и утверждений о версиях/границах дат соблюдай
[ограниченный проверяемый контракт](references/content-claims.md).
Причину окна и совместимость нельзя выводить из наличия даты или целевой версии.

Для `EXCEPTION_BLOCK` используй [статическую модель переходов](references/exception-flow.md):
порядок WHEN, защищённые операции, передачу ошибок и откат. Описывай возможные
пути, а не обязательное выполнение всех операторов; конкретный сбой и значения
локальных переменных на этот момент зависят от выполнения.

Вход: зафиксированные inventory.json и validation_plan.json, путь к SQL и его хеш, срез реестра по [references/facts.md](references/facts.md),
ссылки на нужные SQL/DDL-фрагменты, шаблон блока, список применимых секций,
контекст объекта, run_id, page_id, активный профиль и окончательный путь страницы. Полный SQL доступен по пути, его текст
не требуется повторно передавать в каждый запрос.

Применимость и порядок секций определены в [template.md](template.md).
Сохраняй обязательства плана, их ID и якоря без перенумерации. Каждой извлечённой
формуле/условию нужен точный факт с operation_ids; для view/CTAS нужны выходные
колонки из SELECT. Используй canonical_key/page_id из общего модуля идентичности.
Используй устойчивый ID в заголовке,
например `## Формулы и зависимости {#formulas_dependencies}`. В coverage записывай
именно этот section_id. Для точного фрагмента используй скрытый маркер и fragment_ref
по [references/coverage.md](references/coverage.md). Фрагмент должен раскрывать факт
внутри указанной секции. Не меняй план ради сокращения покрытия.
Не добавляй нерелевантные разделы и не требуй фиксированное число замечаний.
Относительные ссылки строй от каталога окончательной страницы, а не от временной
директории блока или черновика: после публикации они должны оставаться рабочими.

## Работа

1. Проверь, что вход содержит факты для запрошенного блока. При отсутствии реестра
   или нужного определения верни конкретный пробел основному агенту.
2. Используй ID операций и фактов повторно. Для точных формул, условий и EXCEPTION
   дочитай указанные строки SQL. Если реестр расходится с ними, сообщи о расхождении;
   не закрепляй ошибку реестра ради согласованности.
3. Заполни применимые секции по шаблону. Возвращай точные выражения, все значимые
   ветви CASE/IF, фильтры, JOIN-ключи, агрегацию и дедубликацию. Повторяющуюся формулу
   можно описать один раз со всеми местами применения.
4. Укажи подтверждение технических фактов ссылками на файлы/строки. Бизнес-смысл
   из комментария атрибутируй; предположение явно обозначай и не используй как факт.
   Реестр — индекс проверяемых фактов, а не предел допустимого объяснения SQL.
   Следствия guards, присваиваний и RETURN выводи из кода и семантики языка;
   отсутствие отдельного fact_id для следствия не делает его неизвестным.
5. Верни Markdown-фрагмент и отдельную карту покрытия версии 2:
   `schema_version`, `run_id`, `page_id`, `entries`, где каждой записи fact_id
   соответствует непустой массив объектов `{ "section_id": "..." }`.
   Сохраняй одинаковые run_id/page_id между блоками; при сборке объединяются entries,
   а не оболочки. Используй устойчивые ID секций по контракту
   [references/facts.md](references/facts.md). Субагент
   не изменяет файлы: основной агент сохраняет оба результата.

## Большие объекты

Если объём SQL/DDL, число ветвей или формул требует нескольких проходов, разделяй
работу по разобранным операциям/ветвям и семействам KPI, а не по произвольным
диапазонам строк. Это применимо ко всем типам объектов из template.md; фиксированного
порога числа операций нет. Срезы остаются частями одной страницы и одного запуска.

- Сохраняй общий объект, порядок операций, полный план, сигнатуру и финальные блоки.
- Подготавливай срезы контекста с точными source_ref, связанными DDL и зависимостями.
  Сохраняй исходные ID и порядок; включай условия входа в ветвь, область CTE/temp
  и связанные факты, даже если их определение находится за пределами среза.
  Правила срезов — в [facts.md](references/facts.md#срезы-контекста-большого-объекта).
  Покрытие объединённых фрагментов сравнивай с полным независимым планом.
- Счётчики (число INSERT/DELETE/UPDATE), список операций, типы колонок, зависимости
  и основу графа получай из проверенных структурированных данных (inventory, facts),
  а не по приблизительному обзору. LLM объясняет смысл и ограничения, не придумывает числа.
  Укажи область и правило подсчёта; считай уникальные ID в полном реестре, не сумму
  пересекающихся срезов. Число узлов SELECT, включая CTE и операнды UNION, не равно
  числу операторов тела, а число INSERT не определяет число KPI или бизнес-групп.
- Для KPI используй общие подтверждённые формулы с перечнем мест применения и
  отдельными исключениями. Сохраняй читаемость страницы без N копий одинакового SQL
  и без потери разных ветвей. Повторяющуюся формулу описывай один раз, перечисляя
  все места применения с условиями и SQL-ссылками. Сохраняй привязку к operation_ids
  и отдельным fact_id в coverage; одинаковый SQL при разных источниках, фильтрах
  или guards не означает одинаковую семантику. Правила сборки — в
  [coverage.md](references/coverage.md#сборка-большой-страницы).
- Для каждой целевой колонки указывай точный тип, выражение/источник и основание
  по правилам раздела «Типы и параметры» и контракту facts. DEFAULT может задавать
  значение при загрузке, но не заменяет DDL-доказательство типа существующей цели.
  Неизвестный тип отмечай с причиной. Не заменяй колонки масками `tb_*` или группой
  с пустым типом; выражения разных ветвей сохраняй отдельно.
  Для INSERT/UPDATE/MERGE сохраняй `operation.structure.query` с точными SQL,
  source_refs и guards каждой операции. Обобщённые null в колонке допустимы
  только при независимо подтверждённых разных выражениях/типах, с unknown
  сводки и видимыми query-claims всех вариантов: [контракт](references/facts.md).
- Различай неизвестную расшифровку аббревиатуры (например, RR) и доступную формулу;
  неизвестные организационные причины и фактическое поведение. Не заполняй замечания
  догадками ради количества.
- Сформируй граф reads → operation → writes, отдельно calls; дай разрешимые
  SQL/DDL-ссылки и проверенные примеры по сигнатуре. Сохраняй одно run → одна страница.

## Типы и параметры

Перед добавлением unknown проверь исходник и правила установленного языка.
Например, для PL/pgSQL `IF` ветка THEN выполняется только при TRUE; FALSE и NULL
переходят к ELSE, если она есть. Различай `BEGIN`/`END` блока и управление
транзакцией: наличие первого не означает явную транзакцию, а отсутствие
COMMIT/ROLLBACK не означает отсутствие блока. Основания:
[условные ветви](https://www.postgresql.org/docs/15/plpgsql-control-structures.html#PLPGSQL-CONDITIONALS),
[структура блока](https://www.postgresql.org/docs/15/plpgsql-structure.html).
Это правила языка, а не подтверждение версии или совместимости Greenplum.

Используй таблицы из соответствующего блока без конкурирующего формата.

- Разделяй тип целевой колонки/результата и тип выражения. DDL источника не задаёт
  тип колонки уже существующей цели. Для view/CTAS тип результата задаётся SELECT.
- Неизвестный тип — `unknown` с причиной. Однозначно известный тип выражения
  допускается по правилу установленного диалекта или явному приведению.
- Для обычной колонки CREATE TABLE без загрузки тип выражения не применим.
- DEFAULT бери из объявления параметра (включая допустимую в диалекте форму `=`).
  Обработку строкового 'default', NULL и других специальных значений описывай отдельно.
  Отличай IN, OUT, INOUT и VARIADIC: не объявляй OUT обязательным входным аргументом.
- Примеры должны учитывать всю сигнатуру. Не показывай вызов без обязательных
  аргументов как рабочий. PERFORM вызывает функцию внутри PL/pgSQL, CALL — процедуру.

## Зависимости и поток

Бери все reads/writes/calls из реестра, а не только INSERT/FROM/JOIN.
Для MERGE ветви INSERT/UPDATE относятся к цели MERGE; USING — источник.
Физические зависимости, локальные CTE и временные объекты различаются явно.
Диаграмма должна включать применимые операции UPDATE, DELETE, MERGE, CTAS и вызовы,
если они существенны для объяснения; не рисуй выдуманный staging.
Неизвестные эффекты динамического SQL и вызовов отмечай в разделе неопределённостей.

## Профиль

Проектные сущности и ограничения используй только при активном профиле и наличии
соответствующей конструкции в коде. Число INSERT не определяет бизнес-группы.
Комментарии, старые примеры и профиль не разрешают добавлять отсутствующие операции.

## Исполняемые контракты P1

Триггеры, индексы, права и ограничения CREATE/ALTER описывай по
`operations.structure` с `extension_version: 1`; поля и правила связи с планом —
в [references/facts.md](references/facts.md). Сохраняй timing/events, выражения
индексов, WHERE, типы ограничений, привилегии и роли, а также полный DDL.

Сохраняй параметры/RETURNS/volatility, назначения UPDATE/MERGE, INTO/ASSIGN/RETURN,
область CTE/temp и подтверждённые эффекты вызова из AST-инвентаря. Покажи связи формул
и условий с операциями, а не разрозненный список выражений. PRIMARY KEY отличается
от NOT NULL; `expression_status: not_applicable` отличается от неизвестного типа.
Матрица анализа: [sql-support.md](references/sql-support.md).

Для Greenplum сохраняй `execute_on` в объекте и `distributed`/
`storage_parameters` в структуре CREATE/CTAS и определениях таблиц, включая
контекст и восстановленные миграции. Указывай `gp_extension_version: 1`.
Эти атрибуты должны быть видимы в claims страницы; EXECUTE ON не является
динамической командой тела. Версию Greenplum сохраняй как `unknown`, если
нет подтверждения; номер версии PostgreSQL из него не выводится.

Для управляемого обновления используй одну пару маркеров из
[publication.md](references/publication.md). Итоговое слияние выполняется до проверки.
Технический reference adapter использует `page_contract: claims-v1` и видимые таблицы
Fact/Property/SQL value; этот контракт проверяет значения в Markdown. Он не заменяет
читаемое описание и независимый просмотр произвольных пояснений.
