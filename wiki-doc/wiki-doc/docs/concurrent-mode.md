# Одиночный и конкурентный режим

Дата: 2026-09-19. Статус: часть P2-05.

## 1. Общий протокол

Один или несколько агентов используют один код и одинаковые блокировки.
Отдельного переключателя режима нет. Каждый запуск работает в собственном
каталоге с `run_id`; разные процессы не должны совместно менять один bundle.

`publish prepare` сохраняет план публикации и при необходимости объединённый
черновик в каталоге запуска, но не пишет в wiki и не берёт блокировку индекса.
После prepare комплект нужно заново связать manifest и проверить gate, как
описано в [publication.md](../references/publication.md).

`publish publish --dry-run` проверяет gate и текущие снимки, возвращает diff
страницы, Markdown-индекса, метаданных, машинного индекса и lineage. Он не создаёт
wiki, блокировку или журналы, не запускает recovery и не удаляет каталог запуска.
Предпросмотр не резервирует состояние: конкурентное изменение может привести к
конфликту при последующей публикации. Флаги `--dry-run` и `--cleanup-run` допустимы
только для режима `publish`; prepare/recover с ними завершаются ошибкой аргументов.

## 2. Блокировки и публикация

Публикация, восстановление и изменение каталога используют общую файловую
блокировку `.wiki-doc/index.lock` даже при одном агенте. Ожидание по умолчанию —
15 секунд (`index_lock(timeout=15)`); CLI не предоставляет настройки таймаута.
Неуспешное получение блокировки приводит к `WikiConflict`.

Под блокировкой publisher восстанавливает незавершённые транзакции, повторно
проверяет gate и снимки, сохраняет архив комплекта и выполняет транзакцию для
пяти файлов: страницы, `index.md`, метаданных страницы, машинного индекса и lineage.
Замена каждого файла атомарна; состояние всех пяти файлов восстанавливается по
транзакционному журналу. Это не атомарный снимок для читателя, который не берёт lock.

Проверенные конкурентные добавления разных страниц сохраняют обе записи индекса.
Повтор уже опубликованного неизменённого запуска идемпотентен. Изменение той же
страницы после prepare вызывает конфликт. Ручные блоки объединяются на этапе
prepare; последующая ручная правка не перезаписывается молча.

## 3. Восстановление

Транзакционные журналы находятся в `.wiki-doc/journal/<run_id>.json`, а резервные
и подготовленные файлы — в `.wiki-doc/transactions/<run_id>/`.
`publish recover` просматривает незавершённые транзакции под общей блокировкой и
откатывает изменения, если текущие байты соответствуют исходному или записанному
состоянию этой транзакции. Состояния `committed` и `rolled_back` пропускаются.

Если внешний редактор изменил файл, recovery фиксирует `conflict` и сохраняет
резервные копии. Такой конфликт блокирует следующую публикацию до разрешения.
Обычный publish также вызывает recovery до записи новой транзакции.

## 4. Диагностический журнал этапов

`.wiki-doc/journal.jsonl` — отдельный журнал диагностики. Он не используется для
отката или допуска публикации. CLI автоматически записывает:

- `validation` и, если решение выпущено, `decision` при
  `gate --bundle ... --write-decision --root wiki <wiki_dir>`;
- `publish` после публикации, включая повтор с `details.idempotent=true`;
- `publish` с `details.mode=recover` для каждого результата восстановления;
- `error` при ошибке фактической публикации или recovery.

Prepare, dry-run, gate без выпуска решения, lint и query не пишут этот журнал.
API `StageJournal.record` принимает 10 имён этапов, но inventory/plan/draft/lint/
query/regression автоматически не инструментированы. Прямые вызовы Python API
gate/publisher также не добавляют диагностических событий сами по себе.

`event_id` уникален для записи; `run_id` и `page_id` берутся из комплекта, когда
они доступны. Отсутствующий идентификатор остаётся `null`; recovery сообщает
идентификатор транзакции и может не иметь `page_id`. Запись JSONL сериализована
тем же lock и завершается flush/fsync. Повреждённый хвост после сбоя отделяется
новой строкой; читатель пропускает невалидные JSON/UTF-8 строки. Ошибка диагностики
не меняет результат основной операции, поэтому журнал не гарантирует полноту аудита.

## 5. Команды и границы проверки

```bash
# Публикация уже подготовленного и проверенного комплекта
python scripts/wiki_doc.py publish publish <run_dir> --wiki <wiki_dir> --project-root <project_dir>

# Предпросмотр без записи
python scripts/wiki_doc.py publish publish <run_dir> --wiki <wiki_dir> --project-root <project_dir> --dry-run

# Восстановление после сбоя
python scripts/wiki_doc.py publish recover --wiki <wiki_dir>

# Проверка опубликованной wiki
python scripts/wiki_doc.py lint <wiki_dir> --project-root <project_dir> --json
```

Проверки P2-05 выполнены на локальной Windows: конкурентные publisher и JSONL-
писатели, аварийное завершение процесса, восстановление, dry-run и нормализация
эквивалентных Windows-путей. Linux и сетевые файловые системы в этой приёмке не
проверялись. Файловая блокировка согласует процессы, использующие этот протокол;
она не исключает вмешательство внешнего редактора между проверкой и заменой файла.
