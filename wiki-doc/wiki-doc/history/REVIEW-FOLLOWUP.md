## Оставшиеся и новые дефекты

### F1. [P1] Основная страница всё ещё заменяется до валидации

**Где:** [SKILL.md](../SKILL.md), строки 199–218.

Шаг 3.2 требует переименовать `.draft.md` в основную страницу, удалить временную директорию и обновить индекс. Только затем начинается этап 4 — валидация. Примечание в строке 207 запрещает такую замену и требует валидировать черновик, но противоречит непосредственно предшествующим шагам.

Если агент выполнит нумерованную последовательность, непроверенная страница уже попадёт в wiki, а черновик по ожидаемому пути перестанет существовать. При двух запусках для одного объекта `<page_id>.draft.md` также общий, несмотря на изоляцию файлов блоков через `run_id`.

**Исправление:** сборка в `.tmp/<run_id>/page.draft.md` → валидация этого файла → исправления → замена основной страницы и обновление индекса → очистка временной директории. Описать публикацию отдельным шагом после успешной валидации.

### F2. [P2] Поиск DDL целей не включён в фактический алгоритм

**Где:** [SKILL.md](../SKILL.md), строки 42–50, 70–80 и 135.

Этап 2 по-прежнему составляет список из `FROM`/`JOIN` и вызывает finder только для таблиц-источников. Позже в контекст writer предлагается передать DDL источников и целей «из этапа 2», хотя для целей отдельного поиска нет.

Для `INSERT INTO dst SELECT ... FROM src`, где `dst` нигде не читается и её CREATE находится в другом файле, штатная последовательность не обеспечивает поиск DDL `dst`. Новый `unknown` предотвращает угадывание, но доступные типы целевых колонок останутся не извлечены.

**Исправление:** собирать объединение читаемых и изменяемых объектов и искать DDL каждого уникального объекта. Обновить ручной fallback: поиск по содержимому и статусы должны совпадать с finder. Отсутствие результата поиска не считать доказательством внешнего происхождения объекта.

### F3. [P2] Обработка миграций может выдавать неверную актуальную структуру

**Где:** [ddl-finder.md](../ddl-finder.md), строки 50, 72–85.

Поиск по содержимому запускается только при отсутствии файла с подходящим именем. Если `orders.sql` найден, последующие `migrations/042.sql` могут остаться непрочитанными. При нескольких определениях актуальность предлагается определять по времени изменения файлов, а колонки — объединять из всех версий.

Время изменения файла не задаёт порядок применения миграций. Объединение колонок также неверно для `DROP COLUMN`, `RENAME COLUMN` и изменения типа. Например, после `CREATE TABLE ... (legacy int)` и `ALTER TABLE ... DROP COLUMN legacy` объединённый список может сохранить удалённое поле.

**Исправление:** отдельно находить базовое определение и изменения независимо от успеха поиска по имени. Применять CREATE/ALTER в порядке миграций, установленном проектом. Если порядок или целевая версия не установлены, возвращать неоднозначность, а не объявлять версию актуальной по времени файла.

### F4. [P2] Реестр фактов не согласован с контрактами передачи контекста

**Где:** [SKILL.md](../SKILL.md), строки 170–180, 214–218; [doc-writer.md](../doc-writer.md), строки 29–39; [doc-validator.md](../doc-validator.md), строка 64.

В одной последовательности требуется передавать writer полный SQL, а через несколько строк это запрещено. Writer также ожидает полный SQL. Валидатору в штатном вызове передаются старые аргументы и количество INSERT, но не реестр, профиль и DDL, на которых теперь основаны новые проверки.

Из-за этого покрытие по `op_*` не обеспечено описанным вызовом. Отдельно реестр назван источником истины как для writer, так и для validator; необходимо явно проверять его полноту по исходному SQL, иначе одна пропущенная при извлечении операция может исчезнуть из обоих результатов.

**Исправление:** определить один контракт: writer получает срез реестра, пути и нужные SQL-фрагменты; validator получает полный реестр, исходные SQL/DDL и применимый профиль. Добавить сверку SQL → реестр перед сверкой реестр → документация.

### F5. [P2] Шаблоны ответа не поддерживают новые обязательные поля

**Где:** [template/02-schema-signature.md](../template/02-schema-signature.md), строки 49–53 и 84–86; [template/03-entities.md](../template/03-entities.md), строки 19–24 и 74–76; [template.md](../template.md), строки 53 и 80.

Инструкции параметров требуют отдельные графы DEFAULT и поведения при спецзначении, но шаблон ответа сохраняет прежние четыре колонки. Аналогично сущности должны содержать тип целевой колонки и тип выражения, а выдаваемый шаблон всё ещё содержит одну колонку `Тип`. Writer при этом обязан точно сохранять формат таблиц.

**Исправление:** обновить таблицы результатов во всех используемых шаблонах и убрать дублирующиеся определения формата. Саму ошибку трактовки DEFAULT уже можно считать исправленной на уровне смыслового правила.

### F6. [P2] Условные проверки внедрены непоследовательно и слишком сильно ограничивают ревью

**Где:** [SKILL.md](../SKILL.md), строки 239–243 и 298; [doc-writer.md](../doc-writer.md), строка 197; [template/06-misc.md](../template/06-misc.md), строки 51 и 134; [doc-validator.md](../doc-validator.md), строки 48–54 и 152.

Основной сценарий всё ещё требует все 16 разделов и проверки CKR_GP, writer и шаблон — минимум пять замечаний. Они не приведены в соответствие с новым профилем и `not_applicable`.

Есть и новая проблема: для view валидатор оставляет только структуру, зависимости и опциональную диаграмму; проверка формул 3.3 разрешена только `etl_*`. Например, неверное описание `price * quantity` в view оказывается вне явной проверки формул. Функции с нулём операций записи вообще отсутствуют в классификации, а `simple_function` получает ограниченный набор этапов.

**Исправление:** тип объекта должен определять неприменимые разделы, но фактическое наличие формулы, фильтра или вызова должно включать соответствующую смысловую проверку независимо от типа. Согласовать единый набор применимых требований у основного агента, writer и validator.

### F7. [P2] Расширенные операции не доведены до извлечения источников и диаграммы

**Где:** [template/04-formulas-dependencies.md](../template/04-formulas-dependencies.md), строки 37–43 и 57–59; [doc-writer.md](../doc-writer.md), строки 93–96; [template/05-dataflow-diagram.md](../template/05-dataflow-diagram.md), строки 19–23.

UPDATE, MERGE и CTAS добавлены в перечень записи, но источники всё ещё извлекаются только из `FROM`/`JOIN`. Источник простого `MERGE ... USING staging_table` не входит в этот алгоритм. Writer для диаграммы берёт цели только из операций `insert`, поэтому таблица, изменяемая только через UPDATE или MERGE, может пропасть из графа.

**Исправление:** задавать reads/writes/calls для каждой операции в реестре, включая `MERGE USING` и другие формы выбранного диалекта. Строить зависимости и диаграмму из этих связей, без фильтра только по INSERT. Синтаксис и роль USING подтверждаются [документацией PostgreSQL MERGE](https://www.postgresql.org/docs/15/sql-merge.html).

### F8. [P2] Исключение для Audit по-прежнему неоднозначно

**Где:** [rules.md](../rules.md), строки 61–75.

Исходный конфликт SVD → BVD исправлен единой матрицей. Однако Audit-исключение одновременно разрешает обращение к `*_audit_gp_core` и утверждает «Доступ через `_apt`». В примере исключение также показано только через `_apt`. Прямой вызов `PERFORM ..._audit_gp_core.log(...)` поэтому остаётся неоднозначным для проверки доступа.

**Исправление:** явно отделить обычные чтения через `_apt` от разрешённых прямых вызовов процедур/функций аудита в `_core`. Одинаково описать исключение в матрице, пояснении и примере.

### F9. [P2] Новая оценка полноты и критерий готовности противоречат друг другу

**Где:** [doc-validator.md](../doc-validator.md), строки 399–422; [SKILL.md](../SKILL.md), строки 233–243.

Формула `ok / (ok + defect)` исключает все `inconclusive`: одна подтверждённая проверка и 99 неопределённых дадут 100%. Такой процент показывает долю успешных среди проверок с определённым результатом, но не полноту верификации.

При этом пункт 420 требует все применимые проверки в статусе `ok` или `not_applicable`, что фактически запрещает любые `defect`, несмотря на порог 85%. Условие в скобках про `inconclusive` с обоснованием добавляет ещё одну трактовку. Основной сценарий продолжает использовать старый цикл по 85% и не включает новый предел трёх итераций.

**Исправление:** отдельно считать покрытие проверками и долю корректных результатов. Явно определить влияние неопределённости и неблокирующих дефектов на готовность. Использовать один критерий принятия и один ограниченный цикл исправления во всех инструкциях.

### F10. [P2] Контрольные примеры пока не образуют надёжный набор проверок

**Где:** [examples/README.md](../examples/README.md), строки 7, 17–28, 114–126, 169–170 и 222–224.

В папке нет заявленных `.sql` и `.expected.md`: присутствует один README с восемью SQL-блоками. Поэтому указанный прогон файлов с ожидаемыми результатами пока выполнить нельзя.

В ожидаемых результатах есть ошибки:

- Пример 04 требует `INSERT` в `summary_tmp`, хотя эта таблица стоит в `USING` и служит источником. Ветви MERGE изменяют `summary`; отдельного INSERT INTO в примере нет. Роли подтверждены разбором фрагмента в SQLGlot и [документацией PostgreSQL](https://www.postgresql.org/docs/15/sql-merge.html).
- Пример 01 заявлен как отсутствие DDL цели, но сам содержит `CREATE TABLE ... AS SELECT`. Для CTAS типы колонок определяются выходом SELECT; отсутствие отдельного CREATE с явными типами не означает отсутствия определения цели. См. [документацию CREATE TABLE AS](https://www.postgresql.org/docs/current/sql-createtableas.html). Для проверки отсутствующего DDL нужен INSERT в заранее существующую таблицу без её определения в наборе.
- Пример 06 содержит `...` вместо тел функций и является наброском, а не полноценным SQL-файлом для проверки.

**Исправление:** создать реальные входные файлы и проверенные ожидаемые факты, исправить роли источников/целей и обеспечить минимальные зависимости для выбранного способа тестирования. Проверять наблюдаемые факты, а не только наличие заголовков.

### F11. [P2] Профиль содержит неверную информацию о поддержке MERGE

**Где:** [project-profile.md](../project-profile.md), строка 57.

Указано, что в PostgreSQL MERGE отсутствует «до 17», хотя команда есть уже в PostgreSQL 15. Это подтверждается [официальной документацией PostgreSQL 15](https://www.postgresql.org/docs/15/sql-merge.html). Для Greenplum возможность MERGE также заявлена без версии продукта, поэтому её нельзя применить как правило совместимости конкретного проекта.

**Исправление:** исправить информацию о PostgreSQL и указать фактическую версию Greenplum проекта; поддерживаемые конструкции определять по этой версии.
