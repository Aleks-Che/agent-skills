# Проверка артефактов P0-01

`scripts/artifact_schema.py` проверяет форму JSON и объявленные ссылки. Он не
анализирует SQL, не пересчитывает решение о готовности, не проверяет истинность
текста и не разрешает публикацию. Даже при `valid: true` результат содержит
`publication_authorized: false`. Независимое построение плана, проверка файловых
доказательств и полный gate относятся к P0-03, P0-04 и P0-05.

## Запуск

Команды выполняются из корня пакета:

```text
python -m pip install -r requirements.txt
python scripts/artifact_schema.py <run_dir>
python scripts/artifact_schema.py <run_dir> --artifacts facts coverage validation
python scripts/artifact_schema.py --migration-manifest examples/migrations/manifest.json
```

Без `--artifacts` обязательны facts, coverage, validation, validation_plan,
manifest, inventory и decision. Отсутствующий файл — ошибка. Для ещё не завершённого
этапа укажи нужные артефакты явно: результат помечается `mode: partial`. Все уже
существующие известные артефакты также проверяются; наличие некорректного decision
нельзя скрыть выбором только facts. Пустой каталог не проходит проверку.

Зависимости ссылок сохраняются при частичной проверке: coverage требует facts;
обязательство с источником inventory требует inventory; plan_check_id требует
соответствующую запись validation_plan. Частичный этап не создаёт фиктивные
manifest/decision ради прохождения команды.

Код выхода 0 означает корректную форму и связи выбранного этапа; 1 — нарушение
контракта, отсутствующий обязательный файл или битая ссылка; 2 — ошибка чтения,
JSON, зависимостей, установки схем или CLI. Повторные ключи JSON и NaN/Infinity
отклоняются. UTF-8 с BOM поддерживается. Схемы поставляются локально; отсутствующая
схема не пропускается молча.

## Общие связи

Все семь артефактов запуска имеют `schema_version: 2` и один `run_id`.
coverage, validation, validation_plan, manifest и decision имеют общий page_id.
У документируемого объекта facts его известный page_id должен совпадать; page_id
контекстного объекта может быть другим. Неопределённая идентичность может быть
представлена null в facts, но проверка формы не разрешает её публикацию.

В facts все категории массивов обязательны; documented_object_ids непустой,
уникальный и ссылается на objects. Все ID фактов уникальны между категориями.
Типизированные ссылки проверяются по [facts.md](facts.md); весь вспомогательный
context.sql не становится обязательной областью страницы.

coverage.entries связывает существующий fact_id с непустым массивом секций/фрагментов.
Существование секции и соответствие её содержания факту ещё проверяет содержательный
валидатор; программная проверка Markdown относится к P0-05/P1-02.

## Независимый инвентарь и план

inventory содержит inputs, dialect, documented_subjects и items. documented_subjects —
выбранные объявления/области исходного SQL, а не ID из facts. Каждый item имеет
source_ref и anchor из object_or_scope, construct и ordinal. Комбинация пути файла
и этих трёх полей уникальна; вложенная область может отличаться от имени внешнего
документируемого объекта. Неразобранные области фиксируются в coverage_notes.

Каждая запись validation_plan.required_checks содержит уникальный id, rule_id,
subject, source, applicable и blocking. Значения applicable/blocking обязательны:
JSON Schema не заполняет default вместо генератора. subject описывает независимый
предмет проверки, а не требует существующего факта.

Источники обязательства: inventory, object_type, section, profile. Для inventory
обязателен inventory_anchor с полями path, object_or_scope, construct и ordinal,
который разрешается в inventory.items. Для других источников этот anchor не нужен.
Пример одного обязательства:

```json
{
  "id": "operation:select:1",
  "rule_id": "operation",
  "subject": "core.calc()/SELECT/1",
  "source": "inventory",
  "inventory_anchor": {
    "path": "source.sql",
    "object_or_scope": "core.calc()",
    "construct": "SELECT",
    "ordinal": 1
  },
  "applicable": true,
  "blocking": true
}
```

Проверка этой ссылки не доказывает независимость или полноту предоставленного
инвентаря. Его построение по SQL и политика обязательности ещё не реализованы.

## Отчёт, manifest и решение

validation.checks содержит уникальные id и, если результат относится к плану,
plan_check_id со ссылкой на required_checks.id. Дополнительное замечание может
не ссылаться на план. Отсутствие результатов обязательств и вычисление критичности
проверяются будущим gate; P0-01 проверяет существование явно записанных ссылок.

manifest.artifacts содержит ссылки на facts.json, inventory.json,
validation_plan.json, coverage.json, validation.json и page.draft.md в каталоге
запуска. Ссылки имеют path/sha256; подмена имени артефакта другим файлом отклоняется.
sql_files, контекст и версии инструментов объявляются отдельно. created_at имеет
формат даты со временем и часовым поясом. Общий путь исходника не может иметь
разные объявленные хэши внутри одного запуска.

decision — отдельный артефакт с ссылками-хэшами на manifest и validation.
blocking_defects/blocking_inconclusive ссылаются на validation.checks[].id.
На этапе P0-01 проверяются формат этих полей и разрешение ID, но не действительность
хэшей, арифметика метрик или правомерность ready.

Manifest миграций имеет собственную схему без run_id/schema_version запуска.
ordered_files — непустой упорядоченный список без повторов; пути разрешаются
относительно его файла. Допустимый `../baseline/orders.sql` не запрещён проверкой
формы. Чтение миграций и восстановление DDL выполняются отдельным этапом.

## Переход со старого формата

Версия 1 и документы без версии читаются только для диагностики; валидатор выдаёт
ошибку, не изменяя вход. Сохранение старого отчёта или добавление schema_version
не означает новый допуск. Старый validation_gate.py остаётся расчётчиком по отчёту.

Для перехода сохрани исходный комплект, затем по SQL/DDL восстанови область,
единый run_id, уникальные ID и типизированные ссылки; добавь wrapper coverage,
метаданные validation и отдельные основания каждого известного типа колонки.
Перечитай исходники для реальных source_refs/sha256. Не генерируй фиктивные ссылки
или хэши и не конвертируй прежнее ready автоматически. После восстановления
выполни проверку контракта и содержательную валидацию заново.

Полный небольшой пример формы и связности:
[tests/fixtures/artifacts/valid](../tests/fixtures/artifacts/valid).
Его служебные версии синтетические; это тестовые данные, не опубликованный комплект.
