# Контракт реестра фактов (версия 2)

Реестр — рабочий результат анализа, а не замена исходного SQL. Источник технических
фактов — выбранная ревизия SQL/DDL. Валидатор проверяет полноту реестра независимо.

## Версия и идентификация запуска

Каждый реестр принадлежит конкретному запуску документирования:

- `schema_version`: **2** — обязательное поле.
- `run_id`: UUID запуска. Все артефакты одного цикла (facts, inventory, validation_plan,
  coverage, validation, manifest, decision) должны совпадать по `run_id`.
- Схема: `schemas/facts.schema.json`.

## Структура

Сохраняй реестр как JSON. Ниже показана форма, а не валидный заполненный документ:
замени хэш и заполни область, входы и объекты; все семь массивов категорий обязательны,
даже когда некоторые из них пусты. Готовый пример — в
[tests/fixtures/artifacts/valid/facts.json](../tests/fixtures/artifacts/valid/facts.json).

```json
{
  "schema_version": 2,
  "run_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "dialect": {"name": "postgres", "version": "unknown"},
  "profile": null,
  "documented_object_ids": [],
  "inputs": [{"path": "sql/load.sql", "sha256": "<64-hex-chars>"}],
  "objects": [],
  "definitions": [],
  "operations": [],
  "columns": [],
  "formulas": [],
  "conditions": [],
  "unknowns": []
}
```

### Объекты и определения

`documented_object_ids` задаёт область страницы. Срез реестра содержит её объекты,
операции и необходимые определения зависимостей. Соседняя функция в том же файле
или CREATE из context.sql не требуют описания на этой странице только из-за наличия
в inputs. Анализируемый эффект вызываемой функции помечай как эффект вызова,
сохраняя связь с определением и не смешивая его с прямыми операциями вызывающего объекта.

- `objects`: `id`, `kind` (table/view/materialized_view/function/procedure/migration),
  `schema`, `name`, каноническая сигнатура для routines, `page_id`, `source_refs`.
  Неизвестная схема не подставляется из похожего имени.
- Для локальных объектов допустимы `kind: cte` и `temp_table` с обязательными
  `scope` (ID содержащего объекта) и `physical: false`. Это минимальный контракт
  областей видимости; расширенная модель жизненного цикла относится к P2.
- `definitions`: `id`, `object_id`, `status` (resolved/not_found/ambiguous/external),
  найденные файлы и `source_refs`, `revision`, установленный `migration_order`,
  восстановленная структура или явно отделённые варианты. Правила статусов — в
  [ddl-finder.md](../ddl-finder.md).
- `migration_order`: упорядоченный массив путей из `inputs` либо null, если порядок
  не установлен. Для `resolved` нужны непустые `source_refs`; для `not_found`
  допускается пустой список. `structure` содержит текст восстановленной структуры
  или вариантов; не подменяй его ссылкой на произвольный новый формат.
- Каждый `source_ref`: путь относительно проекта, `start_line`, `end_line`,
  `sha256` (64 hex-символа, хеш байтов файла). Для определения из другого файла
  нельзя использовать только номер строки без пути.

### Операции и связи

Для каждого исполняемого оператора запиши:

- уникальный в данном снимке `id` (например `op_001`), `kind`, `source_refs`;
- `reads`, `writes`, `calls` — массивы ссылок на объекты;
- `scope` (ID содержащего объекта), `order` (целое от 1) и `condition_ids` для
  IF/CASE/циклов/обработчиков ошибок; reads/writes/calls/condition_ids обязательны,
  пустой массив означает отсутствие связей;
- `transforms`: точные выражения, JOIN-ключи, фильтры, агрегация и дедубликация;
- `dynamic`: false либо объект `{ "template": "...", "unresolved_parts": ["..."] }`
  с подтверждённым шаблоном и нерешёнными частями. Boolean true без описания недопустим.
- `kind` выбирается из перечисления схемы; для конструкции вне перечисления
  используй `OTHER` и обязательный `kind_detail`. Это фиксирует границу классификации,
  а не подтверждает поддержку синтаксиса экстрактором.

Идентификатор операции стабилен между блоками одной генерации. При изменении SQL
перестрой затронутые факты и покрытие; номера строк не являются вечными ID.

Учитывай чтение в выражениях, FROM/JOIN, UPDATE FROM, DELETE USING, MERGE USING,
CTE/подзапросах, CTAS и возврате функции. MERGE читает USING-источник, а его ветви
изменяют **цель MERGE**. UPDATE может читать прежние значения изменяемой таблицы.
DDL-изменение — write структуры, а не обязательно write строк.
PERFORM вызывает функцию, CALL — процедуру. Вызов не доказывает побочных эффектов:
не добавляй writes вызываемой функции без анализа её определения.

Различай физические таблицы, временные объекты и локальные CTE. Одно имя CTE
в разных областях видимости — разные локальные объекты. Реестр сохраняет их связи,
а внешние зависимости разворачивает до физических источников.
Для одного объекта допустимы одновременно reads и writes.

### Колонки, формулы и условия

- `columns`: `id` (например `col_001`), `object_id`, `name`, `type_target`,
  `type_expression`, `expression`, `source_columns`, `nullable`, `default`, `description`.
- `type_target`, `type_expression` и `source_refs` обязательны. Для **каждого
  непустого утверждения о типе** укажи отдельное доказательство в
  `type_evidence.type_target` и/или `type_evidence.type_expression`:
  `{ "kind": "declaration", "source_refs": [...] }`. Виды: declaration
  (DDL/RETURNS), expression (правило диалекта), comment, inferred.
  Одна общая строка `type_evidence` не различает доказательства двух типов.
  Комментарий и inferred не подтверждают SQL-тип; содержательный валидатор
  проверяет достаточность основания. Для неизвестного типа null доказательство
  не выдумывается, причина описывается в unknowns.
- `type_target` определяется DDL цели, RETURNS для результата routine или
  выходом запроса для view/CTAS. Тип выражения не подменяет тип существующей цели.
- Неизвестное значение — JSON null с причиной в `unknowns`; в Markdown — `unknown`.
  Для обычной колонки таблицы без вычисления тип выражения — «не применимо».
- `formulas`: `id` (например `formula_001`), точное выражение, `source_refs`,
  используемые поля, `condition_ids`, операции использования.
  Включай арифметику, агрегаты и оконные выражения, а не только CASE.
- `conditions`: `id` (например `cond_001`), точное условие, `source_refs`,
  связанные операции. Сохраняй порядок CASE, границы интервалов и семантику NULL;
  не превращай IF в безусловный шаг.
- `unknowns`: `id` (например `unknown_001`), что неизвестно, причина, связанные факты,
  влияние на объяснение. Неизвестность записи по динамическому имени отличается
  от отсутствия DDL её колонок.

Все ID — непустые строки, уникальные во всём реестре, включая объекты и определения;
числовые суффиксы в примерах не являются обязательным синтаксисом. `object_id`,
`scope`, reads/writes/calls ссылаются на objects; `condition_ids` — на conditions;
`operation_ids` — на operations; `source_columns` и `column_ids` — на columns;
`related_facts` — на любую категорию фактов. `used_fields` хранит текст имён SQL,
а `column_ids` — ссылки, когда колонки установлены. Не создавай фиктивную колонку
ради ссылки: недостающие данные отражай в unknowns.

Каждый source_ref должен совпадать с объявлением пути и хэша в inputs;
`end_line >= start_line`. Это проверка внутренней согласованности: реальное
существование файла, содержимое строк и хэш его текущих байтов проверяются отдельно.

Для CTAS/view известные типы выражений можно определить без отдельного CREATE TABLE
со списком типов. Например, в PostgreSQL `now()` даёт timestamptz, явный `::date`
даёт date. Неизвестные типы остальных выражений остаются неизвестными.
Бизнес-названия по комментариям сохраняют источник; конфликт комментария с SQL
отражается явно, техническая логика описывается по SQL.

## Карта покрытия (версия 2)

Writer возвращает Markdown и JSON отдельно. Карта покрытия — обёртка с версией,
`run_id` и `page_id`:

```json
{
  "schema_version": 2,
  "run_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "page_id": "function+core+calculate_total",
  "entries": {
    "op_001": [{"section_id": "dependencies"}],
    "formula_001": [{"section_id": "formulas"}],
    "unknown_001": [{"section_id": "uncertainties"}]
  }
}
```

Каждая ссылка должна вести к реально существующей секции через `section_id`.
Используй стабильные идентификаторы секций, а не только человекочитаемые заголовки.
Карта не подтверждает точность текста сама по себе: валидатор сверяет содержание
секции с SQL/DDL. Используй ID внутри карты; включать служебные ID в читательскую
страницу необязательно.

Схема: `schemas/coverage.schema.json`.
