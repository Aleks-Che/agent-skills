# Подготовка, публикация и восстановление

Все изменения wiki выполняет `scripts/publish.py`. После генерации, **до окончательной
содержательной проверки**, выполни:

```text
python scripts/publish.py prepare <run_dir> --wiki <wiki_dir>
```

Команда сохраняет `publication.json` и окончательный `page.draft.md` после слияния.
План привязывает UUID, страницу, канонический ключ, wiki root, хэши черновика,
текущей страницы/индекса/metadata и ожидаемое отсутствие новых файлов. Его включает
`bundle.py create`; после этого обязательны содержательный отчёт и полный gate.
Изменившийся при слиянии черновик проверяется заново. `prepare` сам не даёт ready.

Явная управляемая область:

```markdown
Ручное вступление
<!-- wiki-doc:managed begin -->
Генерируемое содержимое
<!-- wiki-doc:managed end -->
Ручные примечания
```

Предыдущая проверенная страница из архива служит базой сравнения. Внешние ручные блоки
сохраняются; одновременные изменения внутри управляемого блока дают конфликт. Страница
без базы и без явной области не считается целиком управляемой. Конфликт не стирает
текущую страницу или входящий черновик. Добавление текста после неизменной прежней базы
тоже сохраняется. Нужна одна пара маркеров; сложное слияние выполняется явно до нового gate.

```text
python scripts/publish.py publish <run_dir> --wiki <wiki_dir> --project-root <project_dir> --dry-run
python scripts/publish.py publish <run_dir> --wiki <wiki_dir> --project-root <project_dir>
python scripts/publish.py recover --wiki <wiki_dir>
```

Передавай те же `--profile` и `--policy`, что использовались при проверке. Dry-run
показывает diff страницы, Markdown-индекса, metadata, машинного индекса и lineage;
не создаёт даже lock-файл в wiki.
Обычная публикация под межпроцессной блокировкой повторяет полный gate и проверку
снимков. Конкурентное добавление другой подтверждённой страницы в индекс допускается;
чужое изменение индекса или той же страницы требует новой подготовки.

Архив и metadata: `.wiki-doc/runs/<run_id>/`, `.wiki-doc/pages/<hash>.json`.
Staging/backup находятся на том же томе в `.wiki-doc/transactions/<run_id>/`.
Журнал `.wiki-doc/journal/<run_id>.json` проходит состояния `prepared`, `page_replaced`,
`index_replaced`, `metadata_replaced`, `machine_index_replaced`, `lineage_replaced`,
`committed`. Все пять файлов входят в один write set. Ошибка построения графа
возникает до их замены. Явный `index.py --write` использует тот же lock и отдельный
восстанавливаемый journal для пары JSON. Старые журналы из трёх файлов читаются recovery.
Повтор committed-запуска восстанавливает отсутствующие или устаревшие JSON-кэши.
Записи flush/fsync и отдельные
замены файлов не образуют общей атомарной транзакции: после падения процесс восстанавливает
согласованное старое состояние, определяя фактические байты по хэшам, включая падение
до записи следующего состояния журнала. Новая публикация сначала запускает recovery.

Откат проверяет весь набор целей и backup до записи; чужие байты сохраняются как
`conflict`. Журнал, архив и backup остаются для диагностики. Повтор committed-запуска
не создаёт дубль. По умолчанию временный запуск сохраняется; `--cleanup-run` удаляет
только проверенный `<wiki_dir>/.tmp/<run_id>` после commit, при совпадении с архивом.

Испытания выполнены на Windows с настоящими файлами, двумя процессами и `os._exit`
между заменами. Ветка POSIX есть, но не объявляется испытанной. Внешний редактор,
не соблюдающий lock, может попасть в короткий интервал между проверкой и заменой;
абсолютной защиты от такой гонки и от аппаратной потери записи нет. Последующая
обнаруженная чужая правка никогда не перезаписывается recovery автоматически.
