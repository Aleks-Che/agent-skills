# Регрессионный цикл

[cases.json](../examples/cases.json) задаёт 12 случаев и 15 отдельных предметов страниц.
Для каждого случая в `examples/expected/<case>/` отдельно заданы факты, правила,
решение, утверждения страницы и негативные мутации. Эти ожидания не входят во вход
генератора. Они написаны по SQL и используются проверяющей стороной.

Q-набор задан отдельно в `examples/cases-q.json`. Его JSON-ожидания выпускаются
из авторских констант `examples/expected/_authoring.py`; при изменении ожидания
обновляются и константы. Тест воспроизводимости сверяет все 55 JSON-файлов.
Нормализованная запись DATE/CAST и формул согласуется также с селекторами мутаций;
исходный смысл и основания остаются в `assertions.json`. Поле ожиданий `dialect`
проверяет имя и версию отдельно от наличия технических unknown-фактов.
Удалять required rule только потому, что текущий анализатор его не выпустил,
нельзя: применимость сверяется с SQL и контрактом правила. Поле
`unknown_required` требует хотя бы один unknown и не устанавливает его смысл;
привязки типов проверяет gate, а содержательные утверждения — отдельная приёмка Q-07.

```text
python scripts/run_regression.py --mode reference --output <new_workspace> --repeats 3
python scripts/run_regression.py --mode saved --output <same_workspace> --repeats 3
python scripts/regression_mutations.py <workspace>/regression-report.json --expected-root examples/expected --output <new_mutation_dir>
python scripts/regression_publish.py <workspace>/regression-report.json --wiki <new_isolated_wiki>
```

`reference` — детерминированный технический адаптер `build_bundle.py`, а не испытание
LLM writer. Вместе с проверкой сохранённых результатов и независимым содержательным
проходом это явно обозначенный полуавтоматический цикл. Отчёт содержит режим, модель,
настройки, число повторов/исправлений, ошибки и число вариантов фактов/решений по предмету.
После изменений инструкций/шаблонов требуются минимум три прогона всех случаев.

Ожидаемое решение задаётся в `decision.json`: `ready` требует
`publication_authorized: true`, `blocked`/`revise` — false. Успех отрицательного
сценария означает ожидаемый отказ, а не разрешение публикации. Если gate должен
вернуть диагностику, задай точный список строк в `errors` этого oracle; без поля
ожидается пустой список. Посторонний отказ (например, изменённый хеш) и ошибки входного
контракта не засчитываются. В отчёте исходная диагностика сохранена как `gate_errors`.
Проверки: [test_regression_decisions.py](../tests/test_regression_decisions.py).

Автоматические итерации ремонта пока не реализованы. `--repair-iterations` принимает
только 0; ненулевое значение отклоняется до запуска адаптера и создания отчёта.
Поле `repair_iterations: 0` означает отсутствие ремонта со стороны runner, а не
измерение внутренних действий внешнего агента. Пустой набор случаев/предметов
не считается завершённым циклом.

Полный режим через адаптер агента:

```text
python scripts/run_regression.py --mode adapter --output <new_workspace> --repeats 3 --model <model-and-version> --settings "{}" --adapter "[\"agent-cli\",\"{request}\"]"
```

`--adapter` — JSON-массив argv; shell не используется. `{request}` заменяется путём к
JSON версии 1 с `skill_root`, `project_root`, `output_dir`, `sql`, `context`, `subjects`,
`version`, `profile`, `migration_manifest` и необязательным `dialect` (по умолчанию
`postgres`). Для GP явно передавай `greenplum`, не выводи диалект из профиля.
SQL/контекст копируются с сохранением
относительных путей; package содержит только runtime-инструкции, шаблоны и скрипты,
включая `docs/dialect-support.md`, `docs/concurrent-mode.md` и
`docs/answer-templates.md` из ссылок SKILL.md. Эти документы входят в хэш инструкций
manifest; исторический обзор из docs в изолированный пакет не копируется.
В рабочем каталоге нет tests, history или expectations. Это изоляция контекста,
не системная песочница для враждебного CLI. Адаптер должен соблюдать область входов.

Адаптер пишет `<output_dir>/runs.json`:

```json
{"schema_version":1,"runs":[{"subject":"<canonical-key>","run_dir":"0","profile":null}]}
```

Каждый run_dir разрешается внутри output_dir и содержит полный bundle. Все subjects
должны встретиться ровно один раз. Запуск ограничен `--timeout` (по умолчанию 120 секунд
на случай); stdout/stderr и параметры сохраняются. Ошибка/timeout/пропуск объекта —
неуспех. Доступ к внешнему агенту не предполагается автоматически; отсутствие полного
агентного цикла честно отражено в `full_agent_cycle_completed: false`.

Контракт `facts.page_contract = claims-v1` включает проверку видимых таблиц Markdown:
строки Fact/Property/SQL value сверяются с фактами и отдельными ожиданиями. Удаление
строки, подмена значения и согласованная подмена фактов/текста проверяются отдельно.
Содержимое sidecar не доказывает наличие утверждения в странице. Произвольные
пояснения вне контролируемых таблиц требуют независимого содержательного просмотра
по [doc-validator.md](../doc-validator.md); формальная проверка не заявляет понимания
любого текста. Нулевой false-ready относится к размеченному набору мутаций.

## Приёмка мутаций Q-07

`regression_mutations.py` проверяет записи первого повтора. Для каждого исходного
комплекта заново выполняются SQL-gate, независимые ожидания и сверка видимых claims.
Только прошедший положительный контроль с `ready` и разрешением публикации допускает
оценку мутации; даже ожидаемый `blocked`/`revise` для этого непригоден. Исходный отказ
(например, неполный комплект без SQL-вариантов операций) даёт `baseline_invalid`,
не засчитывается как обнаружение и оставляет итоговый `valid: false`.

Аннотация выбирает ровно один факт через `group` и `selector`, затем заменяет
существующее поле по пути `field` (например `structure.arguments.1`) на `value`.
Селектор без совпадений или с несколькими совпадениями, опечатка в пути и замена
значения на него же — `invalid_mutation`. Для одноимённых колонок/CTE уточни
селектор по выражению, области или порядку исходной операции. Не выбирай первую
попавшуюся запись молча. Аннотации Q-набора меняются через `_authoring.py`.

Оба режима создают отдельные комплекты: `text-only` меняет видимые claims,
`coherent` — также факты и coverage. Validation и manifest строятся заново через
реальный checker и gate; заранее проставленный defect не используется как тест.
Отчёт сохраняет ошибки и слой обнаружения (`visible_claims`, `sql`, `schema`, `profile`);
отказ только из-за посторонней ошибки не засчитывается (`unattributed_rejection`).
Отклонение схемой учитывается отдельно от независимой сверки смысла с SQL.
`profile` означает расхождение наблюдения доступа с подтверждёнными правилами
активного профиля, а не произвольный отказ при загрузке его файла.

`mutations` — число запланированных проверок в двух режимах; `tested_mutations`
и `untested` показывают фактический охват, `detected` — объяснённые отказы.
`false_ready_rate` считается только по запущенным мутациям и равен null без них.
Нулевой false_ready при непроверенных случаях не означает успешную приёмку.
Ошибка генератора не пропускается молча: она попадает в `input_errors`.

ID D01–D11 в аннотациях не доказывают выполнение всех подпунктов матрицы ревью.
Неподтверждённая совместимость, выдуманная причина окна и неверный пример (D12),
произвольная проза, число KPI и смысл рёбер графа требуют отдельных содержательных
мутаций. `facts.dialect` существует, но изменение его версии не равно проверке
утверждения о совместимости в видимом тексте. Проверка эквивалентных заголовков и
форматирования claims не подтверждает принятие любого равнозначного объяснения.
`ClaimTableMutationTests` проверяет неизвестное поле claims, замену SQL-условия
и имени объекта; эти три теста не доказывают содержательную приёмку D12.
Возврат исходных байтов — повторный положительный контроль, а не новый
эквивалентный вариант. Отсутствие цели мутации считается ошибкой теста, не skip.

`D12ProseMutationTests` и `test_q07_content_review.py` проверяют ограниченные
утверждения о версии, сравнения дат и сигнатуры SQL-примеров. Их границы заданы
в [content-claims.md](content-claims.md). Это дополнительные проверки, которые
не входят в 40 аннотированных мутаций и не закрывают причину окна D12 или
произвольную семантическую эквивалентность. Положительный контроль должен сохранять
смысл проверяемого утверждения, а не просто избегать распознаваемого паттерна.

Для приёмки/CI выбранные сгенерированные страницы проверяются происхождением:
`wiki_doc.py provenance --wiki-root <wiki> --page <page_id> --project-root <project>`;
отсутствие metadata — неуспех, обычный lint по-прежнему не заменяет эту проверку.
Подготовка запуска — `wiki_doc.py prepare`, продолжение — `verify-run`/`resume`/
`finalize` со статусами prepared/verified/completed, blocked и needs_action.
Автоматический writer/validator не подменяется reference-адаптером; контракт и
коды — [artifacts.md](artifacts.md).
